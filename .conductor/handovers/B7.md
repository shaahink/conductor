## Weak / deferred (not safely fixable in this session)

### D-01: Built-in/disk persona prompt divergence
The 9 built-in strings in `PersonaRegistry.BuiltIns` are shorter rewrites of the 9 disk files at `plans/personas/*.md`. Two copies of the same content exist. If someone customises a disk file, the fallback becomes a *different* prompt, not a degraded copy. Risk: an operator edits a disk file and assumes the built-in is equivalent. Mitigation: the disk file always wins when present. **Followup (B8 or B12):** generate built-ins from disk files at build time or eliminate built-ins in favour of embedded resources.

### D-02: Persona system prompt leakage into non-deliver sessions
`Vars()` (which resolves persona) is called by `Fix()`, `Resume()`, `Audit()`, and `Advisor()`. This means an audit session for an "architect" stage gets TWO system prompts prepended: the architect persona then the audit template. The merge order (persona → session template → contract rules) means the session template's role wins, but the prompt is longer than intended. The audit template explicitly says "You are an AUDIT session" so the leftover persona prefix is noise, not confusion. **Followup (B8):** consider adding a `persona` boolean parameter to `Render()` to suppress persona injection for non-deliver session types.

### D-03: PersonaRegistry has no logger in production
The Orchestrator creates `new PersonaRegistry(plan)` (no logger), so persona resolution warnings (missing file, empty file, path traversal, unknown persona) produce no log output. The warnings only fire in test paths where `ILogger<PersonaRegistry>` is injected. Fixing this requires either passing `ILoggerFactory` through the Orchestrator or changing the PersonaRegistry constructor to accept the non-generic `ILogger` — a design choice best made in B2's DI overhaul or B8. **Followup (B8):** wire PersonaRegistry into DI via `ILoggerFactory` so persona warnings reach the conductor log.

### D-04: No persona-name validation beyond path safety
Persona names containing control characters, newlines, or excessively long strings aren't validated. They fail safely (the file won't exist → falls back to built-in → or returns null with warning), but the error messages could be confusing. Low risk; the names come from plan JSON (trusted config), not user input. **No followup needed** unless external persona sources are added.

### D-05: Merge() doesn't deep-clone lists
`AgentConfig.Merge()` assigns `o.Args` directly: `Args = o.Args.Count > 0 ? o.Args : Args`. If the caller mutates the returned Args list, the original plan.Agent.Args is NOT affected (we return a new AgentConfig with a reference to the override's list). But the override's own Args is shared. This is safe because Merge() always returns a fresh instance and the override AgentConfig comes from deserialization (not shared). **Low risk; no followup needed.**

## Risks for B8

1. **Persona in audit/advisor prompts (D-02)** — B8 introduces reflection/self-review where persona noise could confuse the review model. Test with persona-heavy stages.
2. **Built-in/disk divergence (D-01)** — B8's reflection prompt might reference persona system prompts; if they differ from disk, the reflection could produce a mismatched analysis.
3. **Logger wiring (D-03)** — B8's DI work should include `PersonaRegistry` in the container so warnings are visible.
4. **Stage-level persona override was only tested at the JSON/unit level** — no integration test exercising the full prompt pipeline with a persona. A dry-run with `--dry-run` against a persona stage would verify the compiled prompt. **Recommend B8's opening session do a dry-run smoke test.**
