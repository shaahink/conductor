## What is solid and proven

  `powershell`/`bash`/`sh` with correct exit-code capture. `ProcessRunner.DefaultShell` auto-detects
  by OS (`powershell` on Windows, `bash` elsewhere). Unknown shells return exit code -1 with an error
  message (never throw). `RunPowerShell` delegates to `RunShell("powershell", ...)` — zero regression
  for existing callers. `GateRunner.RunOne` resolves `g.Shell ?? ProcessRunner.DefaultShell`.
  `GateConfig.Shell` is `string?` (deserializes correctly; `null` = auto-detect). Evidence:
  `src/Conductor/Core/ProcessRunner.cs:70-86`, `src/Conductor/Core/GateRunner.cs:85-86`,
  `tests/Conductor.Tests/B11_1Tests.cs` (15 tests: exit 0/non-zero for all 3 shells, unknown-shell

## Weak / deferred / not fully covered

- **B11.4 acceptance used a fake-agent, not real cTrader credentials.** The end-to-end owner-gate flow
  (block → approve → advance → reconcile verdict committed) was exercised through Conductor, but the
  session work was a synthetic agent writing a fake verdict file — the real cTrader-credentialed
  compare-both path was not exercised. The code paths are proven (the orchestrator + owner-approval
  + state machine are tested at multiple layers), but the credentialed security boundary (cTrader
  login + live data fetch) is unproven. This is reasonable for a code-level acceptance test (the
  stage trap explicitly says blocking on `AwaitingOwner` IS success), but a live-credentialed run
  would bind the full path. This is deferred to the actual Shamshir run, not the Conductor self-plan.
- **Completion scripts are hardcoded (not introspected from Spectre.Console.Cli).** Both PS and Bash
  completion contain manually-maintained verb and option lists. Adding/removing/renaming a command
  requires updating 2 places in `Commands.cs` (the verb string + the option array) and PROGRAM.cs
  (the `AddCommand` registration). The ADR-0003 documents this as intentional (Spectre.Console.Cli
  doesn't expose a command-registry query API at runtime). **Risk:** B12 may add commands — if the
  completion scripts aren't updated, `conductor <new-verb> <TAB>` will silently offer nothing. The
  `B11_2Tests.Completion_Powershell_ContainsAllVerbs` test asserts that the verb list in the output
  contains the word `run`, `doctor`, `completion`, `new-plan`, `tasks`, `replay` — but it does not
  assert exhaustiveness against the Program.cs registration list. A future test should do so.
- **Doctor remaining-stages logic relies on tracker parse which can be incomplete.** If the tracker
  file uses a non-standard format or the stage ID pattern doesn't match, `SafeParseTracker` returns
  null and the doctor falls back to state-only logic (skipped/confirmed stages excluded from
  remaining). This is correct and safe, but a stage whose tracker rows are DONE won't be excluded
  from the remaining list — the doctor will show it as still pending. The preference would be to
  check `ConfirmedStages` (the authoritative source) which is always available. The tracker check
  adds granularity (partial stages) but the fallback is reasonable.
- **BatterySignature unchanged by shell property.** Two gates with identical names/commands but
  different shells produce the same signature, which means the skip-on-green-HEAD cache won't
  distinguish them. Since the shells should produce identical results for identical commands, this
  is correct — adding shell to the signature would break the cache for no benefit. Verified in
  `GateRunner_BatterySignature_UnchangedByShellProperty`.
- **Clean-clone battery verified on same machine only.** B11.3 evidence shows a fresh clone of
  `feat/baton` on the author's machine passes build + test. A truly clean-slate proof would clone
  on a machine without any prior Conductor SDK/tooling. The `.gitignore` + clean-clone protocol
  cover most hidden-state vectors, but a different-OS test (Linux clone + build) would be the
  gold standard.
- **No Unix CI/CD for cross-platform shell verification.** The bash/sh shell dispatch is tested
  only where bash is available on Windows (via WSL/msys). The unit tests for bash/sh gracefully
  skip if the shell isn't present (`BashAvailable()` check). A Linux CI runner would exercise these
  paths continuously. Not a code bug — the dispatch is deterministic — but an integration-test gap.
- **FU-B10-1 (integration harness) and FU-B10-2 (battery collapse token measurement) not cleared.**
  Both were targeted at B11 but are infrastructure/deferred-observation items, not blocking for the
  phase. Remaining open as tracked followups.

## Risks the next phase (B12) should watch

1. **Parallelism + cross-platform gates.** B12's parallel lanes may run on different OSes (if the
   self-plan moves to a multi-machine pool). The `shell` property on gates is OS-aware via
   `DefaultShell`, so a plan authored on Windows with implicit `powershell` gates won't run on a
   Linux lane unless the gates explicitly set `shell: bash`. The self-plan should explicitly set
   `shell` on any gate expected to run cross-platform.
2. **Completion scripts must stay in sync with new commands.** B12 may add commands (e.g.,
   parallel-lane verbs). The completion scripts in `Commands.cs` must be updated in lockstep. The
   existing `Completion_Powershell_ContainsAllVerbs` test should be strengthened to verify
   exhaustiveness against the Program.cs registration list.
3. **Doctor should work with post-B12 state shapes.** If B12 adds new pending fields to `RunState`,
   the doctor's `On resume, this will happen` section must cover them. The current code is
   straightforward to extend (add another `if (state.PendingX is { } x)` block).
4. **No `PlanConfig.Validate()` coverage for `Shell`.** The `Shell` property accepts any string and
   only fails at runtime (exit -1 with "unknown shell" message). A plan validation pass that warns
   on unsupported shells would catch typos early. Low risk (the error message is clear and the
   failure is non-crashing).
