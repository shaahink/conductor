**Verdict:** B3 delivers the *shape* of every requirement — confirm-gating, an owner-gate projection,

sound. But the audit found **two real defects that green gates never exercised**: (1) approving a run

loop**. Both are **fixed in-session** with value-only regression tests, plus three smaller fixes
(rollback `--force` was referenced but never wired; `goto` to a confirmed stage was a silent no-op;
a dead `ControlAction.ApproveOwner`). Gates green: `dotnet build Conductor.slnx` 0w/0e (net10,
warnings-as-errors), `dotnet test Conductor.slnx --no-build` **164 pass** (was 149).

## What is solid and proven (with evidence)

- **Finger-slip confirm-gating is real and unit-locked.** `ConfirmGate.ProcessDestructive` is a pure
  two-key state machine; a single `A`/`K`/`S` press returns `null` (no action), a repeat returns the
  action; any other key cancels the pending confirm. Wired identically into `LiveDashboard` and
  `PlainSink`. CLI destructive verbs (`abort`/`skip`/`kill`/`rollback`) refuse without `--yes` and stamp
  `confirmed`+`intentId` into `control.json`. Evidence: `docs/baton/evidence/B3.1-gate.txt`;
  `ConfirmGateTests` (8 cases incl. `FingerSlipDoesNotAct`/`ConfirmedPathDoesAct`).
- **Owner-gate is a first-class projection, not a bolt-on flag.** `StageConfig.OwnerGate` +
  `RunStatus.AwaitingOwner` + `OwnerApprovalRequested`/`OwnerApprovalGranted` events + a persisted
  `OwnerApprovedStages` list; a green owner-gated stage parks and survives restart. Evidence:
  `docs/baton/evidence/B3.2-gate.txt`; `RunStateTests` (`AwaitingOwnerStatusRoundTripsThroughDisk`,
  `OwnerGateBlocksOnGreenResumesOnApprove`, `OwnerApprovedStagesPersistAcrossRestart`).
- **Budget/approval config + owner-gate flags deserialize correctly.** `LimitsConfig.MaxRunCostUsd`/
  `MaxRunTokens`/`ApprovalMode` and `StageConfig.OwnerGate` round-trip through camelCase JSON with
  correct null/false defaults. Evidence: `docs/baton/evidence/B3.4-gate.txt`; `PlanConfigTests`
  (`BudgetCapsDeserialize`, `BudgetCapsDefaultToNull`, `OwnerGateStageFlagDeserializes`).
- **Persistence of every new control field round-trips.** `PauseAfterStage`, `OwnerApprovedStages`,
  and (new this session) `AwaitingOwnerReason` all survive save/load. `RunStateTests`.
- **The dashboard reflects the new states.** `AwaitingOwner` action bar (`R=approve`), the confirm
  prompt footer. `DashboardRendererTests`.

## What I FIXED in this audit

1. **Park-reason conflation (real, high).** Three code paths set `AwaitingOwner`: an owner-gate on a
   green stage (approve ⇒ **confirm** the stage), approval-mode parking *before* a session (approve ⇒
   **run** the next session), and a budget/token cap tripping *after* a session (approve ⇒ **reset the
   window and continue**). The delivered `ResumeRun`/`AwaitingOwner` handler called `ConfirmStage(...)`
   for **all three** — so approving an approval-mode or budget park **confirmed and advanced past the
   stage without doing the work**. Approval mode was doubly broken: after approval it re-parked
   immediately (the `ApprovalMode` flag was still set), so it could never run a session at all.
   **Fix:** persist *why* we parked (`RunState.AwaitingOwnerReason`), a pure `OwnerApproval.Decide`
   maps reason→outcome, and `Orchestrator.ApproveAwaitingOwner` dispatches: confirm (owner-gate) /
   run-exactly-one-then-park-again (approval mode, via a transient `_sessionApproved` latch) / reset
   `_runCostUsd`+`_runTokens` and continue (budget). **Tests:** `OwnerApprovalTests` (4) lock that
   approval-mode/budget do **not** confirm; `RunStateTests.AwaitingOwnerReasonRoundTripsThroughDisk`
   locks the reason across restart. `src/Conductor/Core/OwnerApproval.cs`, `Orchestrator.cs`, `RunState.cs`.
2. **Control-file null-flag crash (real, high — a loop-killer).** Non-destructive verbs serialise
   `confirmed`/`force` as JSON `null` (nullable `bool`). `ReadControlFile` read them with
   `JsonElement.GetBoolean()`, which **throws `InvalidOperationException` on a `Null` element** — and
   that type was **not** in the catch filter, so a `conductor pause`/`resume`/`approve`/`retry-stage`/
   `pause-after-stage` from another terminal would **crash the running orchestrator's control loop**.
   Green only because the self-run drove control via the TUI `PollControl` path, not the drop-file.
   Proven with a throwaway repro before fixing. **Fix:** extracted a pure, `ValueKind`-guarded
   `ControlFile.Parse` (no field can throw on a null/wrong-typed value) and hardened the catch to also
   ignore `InvalidOperationException` (malformed operator input, per the existing comment’s intent).
   **Tests:** `ControlFileTests` (10) — every non-destructive verb parses with null flags without
   throwing, `--force`/`stageId`/`confirmed` are read, wrong-typed fields degrade instead of crashing.
   `src/Conductor/Core/ControlFile.cs`, `Orchestrator.cs`.
3. **`rollback --force` wired (R3.3 gap).** The delivered rollback logged *“Use --force to override”*
   but **no `--force` flag existed anywhere** — a dirty tree could never be rolled back, contradicting
   R3.3. Added `--force` to the CLI (`control.json` `force`), threaded it through `ControlFile.Parse`
   into the `Rollback` handler; with `--force` a dirty tree is discarded by the `git reset --hard` (and
   the log says so). `Commands.cs`, `Orchestrator.cs`.
4. **`goto <confirmed-stage>` was a silent no-op.** Jumping back to an already-confirmed stage set
   `CurrentStage` but `SelectStage` skips confirmed stages, so nothing happened. Now `goto` un-confirms
   the target (and drops its owner approval) so it actually re-runs. `Orchestrator.cs`.
5. **Dead `ControlAction.ApproveOwner` removed (A1).** Added to the enum but never referenced
   (`approve` maps to `ResumeRun`). `Progress.cs`.

## What remains shortcut / weak / assumed / NOT fully fixed this session

- **No orchestrator-level integration test for the process-control loop.** The `Orchestrator` has a
  heavy constructor (plan/state/sinks/providers/logger) and there is **no test harness** that drives a
  real run. Every B3 "gate" test in `RunStateTests` (`GotoResetsStageState`, `RetryStageResetsAttempts`,
  `RollbackRefusesIfDirty`) is a **state-shape simulation that mutates `RunState` by hand** — it does
  **not** exercise `HandleControl`. `RollbackRefusesIfDirty` in particular only calls `Git.IsDirty(...)`
  and asserts nothing (its own comment admits "the real test is … manual smoke-test"). I fixed the real
  branch logic and locked the *pure* decision helpers (`OwnerApproval`, `ControlFile`), but the
  **park→approve→run→park loop, `goto`, `rollback`, and graceful-cancel are proven only by reasoning +
  the pure-unit slices, not by an integration test.** Followup FU-B3-1.
- **B3.5 graceful Ctrl+C is unproven by any test.** There is **no cancellation test** and **no
  `B3.5-gate.txt`** (evidence exists only for B3.1–B3.4). The DoD called for "cancellation test — state
  saved, resume queued, log flushed, exit code correct". The code path (`Run`’s cancel block +
  `RunSession`’s internal `ct` handling → `QueueResume` + exit 130) looks correct on inspection, but
  it is **assumed, not verified**. Followup FU-B3-2.
- **Budget accumulators are per-process, not persisted.** `_runCostUsd`/`_runTokens` reset to 0 at each
  `Run()` start. The *park* survives restart (`Status=AwaitingOwner` is persisted, so a killed-while-
  parked run stays parked until approved), but a run **killed mid-accrual before it parks** restarts its
  count from 0 — so a run split across restarts can exceed `maxRunCostUsd`/`maxRunTokens` without ever
  parking. Persisting a cumulative run baseline is a design decision (per-process vs per-logical-run).
  Followup FU-B3-3.
- **Rollback (a destructive `git reset --hard`) is not recorded as an event.** The B3.3 trap says
  "log the reset". It is written to `conductor.log` + the structured Serilog sink, but there is **no
  `ConductorEvent`** for it, so the event-log timeline / report / (B6) Telegram will not show a
  rollback. Followup FU-B3-4.
- **Control verbs arriving mid-session are silently dropped.** `retry-stage`/`rollback`/
  `pause-after-stage`/`goto` are guarded `when !inSession`; if issued during a session the `control.json`
  is consumed (deleted) but the guard fails and the operator gets **no feedback**. Low severity (these
  are between-session ops) but poor UX. Followup FU-B3-5.
- **`_sessionApproved`/`_rollbackForce` are transient.** If the process dies between an approve and the
  session running (or between a rollback command and its execution), the action is not replayed and
  requires re-issuing — this **fails closed** (safe), but worth knowing.
- **FU-B2-3 (carried in, owned by B3) was NOT addressed.** Event-log recovery of an orphaned
  `SessionStarted` with an empty `AgentSessionId` still queues a non-resume. Out of this audit’s scope
  (event-log recovery, not process control). Remains OPEN, re-homed.

## Risks the next phase (B4 — TUI overhaul) should watch

- **Do not regress confirm-gating or the `AwaitingOwner` action bar when the TUI is rebuilt.** The
  finger-slip guard lives in `LiveDashboard.HandleInput` via `ConfirmGate` + a `_pendingConfirm` latch,
  and the `AwaitingOwner` case (`R=approve`) is in `DashboardRenderer.ActionBar`. A Layout rewrite must
  carry both forward (ideally re-prove `FingerSlipDoesNotAct` still maps to the new key handler).
- **The process-control loop is under-tested.** If B4/B5 touch `HandleControl`/`Run`, add the
  integration harness (FU-B3-1) first — the pure slices won’t catch a loop regression.
- **`state.json` now carries `awaitingOwnerReason`.** An older state file (null) is treated as an
  owner-gate (the safe default). Keep that fallback if the enum is ever renamed.
