## Architecture decisions

1. **Verify is a new SessionKind**, consumed before Audit but after Deliver. Priority order: Resume → Audit → Verify → Fix → Deliver. This lets the orchestrator interleave verification naturally in the session loop.

2. **Verifier runs only after Deliver sessions** (not Fix, Resume, Audit). `ShouldVerify(rec)` returns true only for `SessionKind.Deliver`. This avoids re-verifying work that's already been audited or that's purely a gate-fix.

3. **Score threshold is per-plan** (LimitsConfig.VerifierThreshold, default 80). Per-stage override not yet wired — StageConfig would need a nullable int, deferred to F7 (gate selection).

4. **Findings route two ways**: score ≥ threshold → findings written to followups.md (via FollowupParser format). Score < threshold → PendingFix.VerifierFindings + PendingFix queue → Fix session.

5. **Advisor verdicts already fully honored** (F4.4). Verified `ApplyVerdict()` in Orchestrator handles all 8 AdvisorAction values — no code change needed.

6. **Handoff fact-check is Verify-scoped** (F4.5). The verify.md template instructs the agent to independently check handoff claims against git log + artifact paths. The verifier's score reflects this check.

## What is solid

- Verifier parsing is robust: handles missing fields, out-of-range scores, non-JSON text, null/empty inputs, JSON embedded in prose
- WriteScore records to the pre-existing scores table (schema was ready since F1)
- ShouldVerify gates non-Deliver sessions by design
- WriteVerifierFollowups appends to followups.md in standard table format
- 626/626 tests pass at 0w/0e (strict Meziantou analyzer ruleset)

## Weak spots / future work

- **No per-stage verifier override.** Plan-level VerifierThreshold works but individual stages can't override. F7 (truth gates + stage config) is the right place.
- **Verifier can double-work.** The agent re-runs gates that conductor already ran. Gate caching by SHA (F7.4) will fix this.
- **Followup file collisions.** WriteVerifierFollowups appends to followups.md without a write lock. Concurrent sessions (parallel audit + verifier) could race. Low risk under sequential delivery, but worth a file-level lock in F7.
- **Verifier model is same as deliver model.** The design doc says "cheap model" for verification — but the plan config doesn't yet support per-role model selection. Pipeline for F5 control plane to add.
- **No truth gates yet.** The verifier re-runs the existing gate battery. True truth gates (product-level assertions) land in F7.3.

## Risks for F5 (Control Plane)

- F5 adds HTTP+SSE on localhost — the verifier's agent output parsing is purely synchronous and file-based, so it won't interfere
- Ensure the control plane doesn't block the main loop (async HTTP hosting)
- Contract tests for the control plane should include a `GET /scores` endpoint since the scores table is now populated
