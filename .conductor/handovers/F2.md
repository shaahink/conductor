## What this audit FIXED

1. **bg natural exit never marked in run.db** (critical) — `McpTaskServer.HandleBgStart` and
   `Commands.ExecuteStart` fire-and-forget tasks did not call `MarkPidExited` after
   `WaitForExitAsync`. A bg process that completed naturally would remain in run.db as
   "not exited" forever, appearing as "dead" (no OS process) but never "exited" — bloating
   orphan queries and confusing status. Fixed: both now call `MarkPidExited(pid, exitCode)` in
   the `Task.Run` closure after process exit, with the `logWriter.DisposeAsync()` moved to a
   `finally` block.
2. **Indentation drift in Orchestrator.cs:763** — the `gatesGreen` condition had 4 extra
   spaces of indentation (12 vs 8), introduced when the condition was widened to include
   `postTrack.StageDone(stage.Id)`. Fixed.
3. **Missing `InvalidOperationException` in bg_stop** — both `McpTaskServer.HandleBgStop`
   and `Commands.ExecuteStop` only caught `ArgumentException` from `Process.GetProcessById`.
   If the process exits between PID lookup and kill, `InvalidOperationException` is thrown.
   Added catch in both places.
4. **Missing `NotSupportedException` in `ReapOrphans`** — `Process.GetProcessById` can throw
   `NotSupportedException` on non-Windows platforms. Added catch.
5. **SanitizeFileName consistency** — evaluated and found functionally equivalent (both
   approaches produce identical results for all valid/invalid char combinations). No fix
   needed.

## Weak / shortcut / not fully covered

| # | Issue | Severity | Why not fixed |
|---|---|---|---|
| W1 | bg_start bypasses `ProcessSupervisor` — bg processes are tracked only in run.db, not in the supervisor's in-memory `_processes` dictionary. They get no JobObject protection (survive conductor crash by design, but also not visible via `ProcessSupervisor.Processes`). | LOW | By design — bg processes are meant to outlive sessions. Reaper handles crash orphans. |
| W2 | Double JobObject in AgentSession — proc is assigned to both the session's local `_job` (line 97) and the supervisor's JobObject (line 98). The second `Assign` silently fails (process already in a job). Supervisor's KILL_ON_JOB_CLOSE doesn't cover agent processes; the local `_job.Dispose()` in `AgentSession.Dispose()` handles it. In-memory and run.db tracking via supervisor still work. | LOW | Harmless — crash safety preserved via local JobObject. Fixing would require removing the local `_job` assignment when supervisor is present, which risks regression. |
| W3 | No test proving bg natural exit → `MarkPidExited` — the fix is correct but lacks a dedicated test. Writing one would require spinning up a truly short-lived process (e.g. `cmd /c exit 0`) and waiting for its log file + DB state. | MEDIUM | Race-y to test; the fix is trivially correct. Worth adding in F3 if stalled processes are a concern. |
| W4 | `ProcessSupervisor.Dispose()` clears `_processes` without calling `UnTrack`/`MarkPidExited` — on clean shutdown, PIDs remain in run.db as not-exited. Next run's orphan reaper cleans them up (gets `ArgumentException` from `GetProcessById` → marks exited). Self-healing but noisy. | LOW | Self-healing. Would add complexity to track dispose vs crash. |
| W5 | `ReapOrphans` only runs at startup — new orphans created mid-run aren't reaped until restart. F3 should poll periodically. | MEDIUM | Design choice — F3 stall detector is the consumer. Not a fix for this session. |
| W6 | No `CancellationToken` threaded through bg_start's fire-and-forget task — the `Task.Run` closure doesn't respect cancellation. If the host process exits, the task is abandoned. The OS cleans up orphaned processes. | LOW | Fire-and-forget by design. Cancelling a bg process contradicts the "background" intent. |

## Risks for F3 (Stall v2)

- **Liveness feed filtering**: `GetAllPids` returns ALL tracked PIDs. F3's stall detector must
  filter by purpose prefix (`bg:` vs `agent:`) since bg processes have different stall semantics.
- **Orphan polling interval**: Reaper is startup-only. If F3 runs long and spawns orphans, they
  accumulate. Add periodic reaping in F3.1.
- **bg process exit races**: The fire-and-forget `MarkPidExited` runs on a ThreadPool thread with
  no synchronisation against bg_stop. If stop and natural exit race, two `MarkPidExited` calls
  could interleave — but the SQL `WHERE exited_utc IS NULL` prevents double-marking.
