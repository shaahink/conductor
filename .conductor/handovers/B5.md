## Weak / shortcut / assumed — cannot fix this session

- **McpCallFinished events are never emitted** in production. The projection and `## MCP` section
  are ready and tested (synthetic streams), but the agent provider doesn't produce these events.
  B9 (MCP task server) must emit them or the MCP metrics section remains inert in real reports.
  This is by design (forward-looking), documented honestly in the event schema comment.
- **Health heuristics proxy through session outcomes + gate failures only.** Tool-level oscillation,
  command repetition within a session, and per-turn context growth are invisible until B9 lands
  per-turn command/tool events. The current heuristics are conservative (no false alarms) and
  the fold contract will accept richer events without change.
- **Confidence counts evidence items by splitting the Evidence column string** — it does not verify
  that referenced paths exist on disk. The gate battery (which re-runs commands) is the truth
  verifier; confidence is a human-auditable count mechanic.
- **`RepoStrip.Compute` catches `Exception`** (RepoStrip.cs:32). The error surfaces in
  `RepoInfo.Error` so it's not silent, but a narrower catch (`IOException` +
  `InvalidOperationException`) would be more precise. Low risk: `ProcessRunner.Run` already guards
  its own exceptions.
- **UI-thread I/O stall when opening modals**: `RepoLines()` and `ConfidenceLines()` call git/tracker
  I/O synchronously from the UI thread when the user presses `B`/`N`. Acceptable for
  once-per-keypress; no observable hang on local repos. Could be made async if it becomes a problem.

## Risks for the next phase (B6 — AFK + Telegram)

1. **B6 MUST call all five projection read methods** when building reports — if it only calls
   `ReadTimeline` + `ReadHealth` (as the `ReportCommand` did before this audit fix), the confidence,
   MCP, and repo sections won't render in Telegram/push reports. Follow the `WriteAndPublish`
   pattern (`Reporter.cs:237`).
2. **The `McpCallFinished` schema exists but is inert** — B6 won't surface MCP data unless B9 lands
   first. If B6 is shipped before B9, the `## MCP` section will always be empty on real runs.
   Consider a tracking followup in `.conductor/followups.md`.
3. **Context-saturation flag trips at 20M tokens** (conservative). F-8 hit ~28.5M on a real Loom
   run, so the threshold is deliberately lower. Monitor for false-positives as provider context
   windows grow.
4. **Heartbeat commits now use `FormatStable`** for the Repo section, which omits the volatile
   HEAD SHA — verify that B6's Telegram push doesn't accidentally undo this dedup by including
   HEAD in a dynamic message.
