## What is solid and proven (with evidence)

- **The decoupling seam is load-bearing, not a facade.** `Orchestrator` no longer calls
  `TrackerParser.ParseFile` anywhere — it holds one `IProgressProvider _progress` from
  `ProgressProviderFactory.Create(plan)` and calls `_progress.Read(plan)` at all 5 read sites
  (`Orchestrator.cs:66,349,398,839,901`). `TrackerParser` is now a thin back-compat facade over
  `MarkdownTableProvider`. Evidence: `docs/baton/evidence/B1.2-gate.txt`; test
  `TrackerParserTests.MarkdownTableProviderIsByteIdenticalToFacade`.
- **Default parse is byte-identical to the pre-B1 hard-coded parser** for real Loom data. The row
  regex is assembled from `ProgressConventions` defaults to the same shape as the old
  `RowRx`/`HandoffRx`; `HandoffWantsHuman` now routes through `Conventions.MentionsHuman` with the
  `HUMAN:` default. Tests: `TrackerParserTests` (unchanged, still green),
  `ProgressConventionsTests.DefaultConventions_AreByteIdenticalToLoomHardcoding`,
  `DefaultConventions_CannotParseHyphenatedId_ProvingConfigIsLoadBearing`.
- **Conventions are genuinely configurable** (stageIdPattern, handoffMarker, humanToken, status
  vocabulary), bind from camelCase plan JSON, and irregular ids (`P-0`, `P3.4b`, `F5`) resolve to the
  right stages. Tests: `ProgressConventionsTests` (7 cases incl. `Conventions_BindFromPlanJson_CamelCase`).
- **Script/PlanCheckpoint providers are resilient by contract.** `ScriptProvider` turns a missing
  command, nonzero exit, timeout, malformed JSON, and null output into a single clear
  `InvalidOperationException` naming the provider + command — never a raw crash (the B1.3 trap).
  `ProgressProviderFactory` is fail-fast on unknown kind / missing config. Tests:
  `ProgressProviderTests` (9 cases, incl. a real PowerShell normaliser driving a Shamshir-shaped
  `PROGRESS.md`).
- **ReDoS ratchet closed (FU-B0-3).** `.editorconfig` MA0009 is now `error`; every tracker/engine
  regex carries `ProgressConventions.RegexTimeout` (2s). Build is green under it.
- **Read-order battery + new-plan work.** `PromptBuilder` renders a bounded ordered `{readOrder}`
  list (empty when unset); `PlanConfig.Validate()` fail-fast checks repo/tracker/agent/{prompt} with
  actionable messages + schema `version`. Tests: `PromptBuilderTests`, `PlanConfigTests`.
- **Shamshir TRACKER template is a real 17-row artifact** that parses via configured conventions:
  `examples/shamshir/parity-pipeline.TRACKER.md`, test
  `ProgressConventionsTests.ShamshirParityPipelineTrackerTemplate_ParsesCorrectly`.

## What I FIXED in this audit

1. **`new-plan --template shamshir` scaffolded an incoherent, undrivable plan (real bug).** The plan
   JSON declared stages `P-0/P0/P1`, but `BuildTrackerMd` hard-coded `S1 NOT STARTED` + `S1.1/S1.2`
   checkpoint rows for *every* template. So the scaffolded Shamshir plan had **zero** checkpoint rows
   under any declared stage → `TrackerSnapshot.StageDone(stageId)` is always false → the stage can
   never complete and the run stalls. Only `--template dotnet` was ever exercised (B1.6 gate), so the
   happy path masked it (A3/A6: an untested executable branch). **Fix:** `BuildTrackerMd` is now
   stage-aware — shamshir emits `P-0 / P0.1 / P1.1` rows + `P-0` handoff matching its stages; the
   S1-family templates are unchanged. Verified by re-running `new-plan --template shamshir` and a
   `--dry-run` (rows parse, `stage → P-0`). Locked by `NewPlanScaffoldTests` (all 4 templates:
   every declared stage must own ≥1 checkpoint row).
2. **Latent byte-identical regression in status classification.** The row regex captures the status
   keyword with its *original* inner whitespace (`IN\s+PROGRESS`), so a hand-edited cell like
   `IN  PROGRESS` (double space) or `IN\tPROGRESS` reaches classification verbatim. The old parser
   used `StartsWith("IN")` and caught it; the new vocabulary keyword is the literal `"IN PROGRESS"`,
   so `StartsWith` silently returned **false** — the active checkpoint would read as not-in-progress
   (exactly the silent-progress-corruption class the stage trap warns about). **Fix:**
   `StartsWithAny` now collapses whitespace runs on both sides before the prefix test (single-space
   path allocates nothing new). Locked by
   `ProgressConventionsTests.InProgress_WithIrregularInnerWhitespace_StillClassifies`.
3. **`new-plan` no longer leaves a half-written scaffold on disk** if the post-write `PlanConfig.Load`
   self-check throws — it deletes the partial files and reports the reason (defensive hardening of the
   A6 self-check).
4. Tidied one misleading comment in `PlanConfig.Validate()` (it claimed to "note" a missing version;
   the default handles it — no behaviour change).

## What remains shortcut / weak / assumed (could NOT be safely fixed here — tracked as followups)

- **FU-B1-1 — `ScriptProvider` cannot distinguish stdout from stderr.** `ProcessRunner.Run`
  interleaves both streams into one buffer, so a script that writes *any* progress/warning to stderr
  corrupts the JSON parse and surfaces as "not a JSON checkpoint array". The provider is resilient
  (clear error, no crash) and the contract ("print ONLY JSON to stdout") is documented, but it is
  brittle. Splitting the streams is a `ProcessRunner` signature change that belongs with B2's
  structured-logging/error-surfacing rework. → **B2.**
- **FU-B1-2 — no `CancellationToken` through `IProgressProvider.Read`.** The whole progress read is
  synchronous; `ScriptProvider` spawns a process with only a timeout, not the run's cancellation
  token, so `Ctrl+C` won't interrupt a long normaliser mid-read. Consistent with the deferred
  sync-over-async posture (FU-B0-1); threading a CT here should land with the B2 async/Host/DI pass.
  → **B2.**
- **FU-B1-3 — `ScriptProvider` trusts checkpoint content shape.** It accepts a JSON array with empty
  ids/status without validation (garbage-in → empty-id rows). Acceptable for a plan-owned script, but
  a stricter contract (reject empty id, unknown status) would fail louder. Low priority. → post-B2.
- **Whitespace fix is scoped to the classification prefix only.** The stored `Status` string still
  keeps its original whitespace (by design, for display fidelity); only Done/Blocked/InProgress/Todo
  detection normalises. If a future consumer string-matches `Status` directly it should normalise too.

## Risks the next phase (B2) should watch
- **The STABLE driver from `master` still parses with its OWN `TrackerParser`** — the in-tree
  `IProgressProvider` seam only judges runs driven by an in-tree build. Any claim about non-markdown
  providers driving a real run is unproven until the driver is rebuilt (out of scope here). The
  self-plan (`plans/conductor.self.plan.json`) uses the markdown-table default, so the stable driver
  drives Baton correctly.
- **`ProgressConventions` caches `_stageRx` in a mutable field and `ProgressConventions.Default` is a
  shared singleton.** The lazy `??=` is benign under today's single-threaded orchestrator (idempotent
  build, Regex matching is thread-safe), but B12 parallelism must not mutate a shared conventions
  instance across lanes.
- **`BuildRowRegex`/`BuildHandoffRegex` build a fresh `Regex` on every `Read`** (not compiled/cached).
  Fine at current call volume; revisit only if a provider read moves onto a hot path.
- **Central package management + InternalsVisibleTo:** this audit added `InternalsVisibleTo` to
  `Conductor.csproj` so tests can exercise the scaffold builders — keep it if B2 restructures projects.
