## What is solid and proven

- **B10.1 — `dependsOn` + ready-stage selection.** `StageConfig.DependsOn` deserializes, validates
  (self, unknown, cycle via DFS), and feeds into `SelectStage()`/`DepSatisfied()`. A skipped stage
  unblocks dependents (matches spec). Evidence: `tests/Conductor.Tests/B10_1Tests.cs` (7 tests:
  cycle, self, unknown, linear-3, diamond, camelCase deser, intermediate cycle).
- **B10.2 — hierarchical stages.** `ParentId` on `StageConfig` + `StageProgress`. Validation catches
  self-parent, unknown parent, and chain cycles. `SnapshotBuilder.ComputeDepth()` walks the chain
  with cycle-guarded visited set. `Reporter.cs` ($5.1) indents stage names in the report;
  `PlanTree.cs` ($5.2) indents stage rows (2sp/depth) and checkpoint rows (depth+1). Evidence:
  `tests/Conductor.Tests/B10_2Tests.cs` (12 tests: validation + depth computation + tree rows +
  camelCase deser).
- **B10.3 — per-stage hooks.** `StageConfig.PreHook`/`PostHook` (both `HookConfig?`) deserialize
  correctly with defaults (cwd=null, timeout=3min). `RunStageHook()` executes via
  `ProcessRunner.RunPowerShell`, capturing exit code + stdout. Pre-hook failure triggers
  `NeedsHuman`; post-hook is best-effort (logged, never blocks). `RunState.PreHookRunStages`
  prevents re-running on resume. Evidence: `tests/Conductor.Tests/B10_3Tests.cs` (13 tests).
- **B10.4 — battery collapse.** `PlanConfig.BatteryCollapse` (default false) prompts the agent to
  skip its own build+test ritual. The session template appends "Do NOT run build or test" when
  enabled; reverts to "Run the gate battery" when disabled. The self-plan has `batteryCollapse:
  true`. Evidence: `tests/Conductor.Tests/B10_4Tests.cs` (5 tests: defaults, true deser, prompt
  insertion/omission, self-plan enforced).

## Weak / deferred / not fully covered

- **SelectStage integration test gap.** The `SelectStage`/`DepSatisfied` logic is tested via model
  validation (`B10_1Tests`) but not through a live orchestrator with `RunState` + tracker. The
  Orchestrator has no integration test harness (a long-standing architectural gap tracked as
  FU-B3-1). The logic is straightforward (one LINQ chain + two lookups) and the model-level tests
  catch structural errors, but a real tracker-based test would lock the ordering contract against
  accidental breakage.
- **`DepSatisfied` treats skipped stages as satisfied without transitive dependency check.** If
  A→B→C and B is skipped, C unblocks even though B's own dependency A may not be complete. This is
  the stated design (B10 spec: "you can't run a skipped stage — treating it as effectively done
  unblocks dependents") and matches prior-stage behaviour (`AllEffectivelyDone`), but it means a
  human skipping a stage mid-chain must understand the dependency graph or risk a downstream stage
  starting before its transitive deps are met.
- **B10.4 token savings are not empirically measured.** The B10.4 spec's DoD calls for "token-per-
  checkpoint measured before/after on a self-run; documented drop." The gate evidence states
  "Measurement will be visible as lower tokens-per-session in the report under B10 sessions vs pre-
  B10 sessions." This is deferred observation — the feature emits the correct prompt note, the
  agent's compliance is at the agent's discretion, and there is no automated metric comparing
  before/after token consumption. The correctness invariant (Conductor's battery is always the
  arbiter) is preserved regardless, so this is a measurement shortcut, not a correctness gap.
- **`HookConfig.TimeoutMinutes = 0` edge case.** Settings timeout to 0 would cause
  `TimeSpan.FromMinutes(0)` = `TimeSpan.Zero` → immediate timeout. This is not validated at plan
  load (no minimum-timeout check). Default is 3 minutes, so only affects a plan that explicitly
  misconfigures it. Low priority.
- **No `PlanConfig.Validate()` check for duplicate `DependsOn` entries.** `["A", "A"]` would create
  no logical error but is wasteful noise. Low priority — DFS cycle detection doesn't trip on it.
- **`ComputeDepth` allocates per call (HashSet + FirstOrDefault O(n·d)).** Called once per stage
  per snapshot (dashboard refresh + report write). For the self-plan (13 stages, max depth 1-2)
  this is negligible. Would become a concern for plans with 100+ stages and deep nesting — could
  pre-compute depths once at SnapshotBuilder level.

## Risks the next phase (B11) should watch

1. **`SelectStage` skip-via-dependency interaction.** B11's Shamshir exercise may involve skipping
   stages with downstream dependents. Verify the `dependsOn` graph visually in the TUI tree (depth-
   based indentation) and confirm a downstream stage becomes selectable only after its upstream is
   confirmed or explicitly skipped.
2. **Pre-hook resume.** If a pre-hook fails and the human resolves the issue (e.g., installs a
   missing tool), the orchestrator must re-enter the stage loop and re-run the hook. Verify this
   path on a real plan with a pre-hook that initially fails then succeeds after operator fix.
3. **Battery collapse + gate additions.** If B11 adds new gates (e.g., cross-platform), confirm
   those gates pass *Conductor's* battery (the sole arbiter under collapse). The agent is told to
   skip its own ritual, but the plan's gate array is the truth.
4. **Hierarchical stage display in headless mode.** The self-plan uses `B10` as a parent for `B10.1`
   through `B10.4`, but the tracker currently uses flat stage IDs. If a future stage adds
   `parentId` chains, the report/SnapshotBuilder must maintain correct depth calculation.
