## What I FIXED in this audit

1. **TelegramService graceful shutdown race** (`TelegramService.cs:41,78-96`): `StopAsync` was
   calling `_cts.CancelAsync()` and returning immediately — `Dispose` could then dispose
   `HttpClient`/`CancellationTokenSource` while the poll/send background loops were still
   using them. Now stores the background `Task` objects and awaits `Task.WhenAll` in `StopAsync`
   so shutdown is ordered: cancel → wait for loops to exit → dispose resources.
2. **Bare catch in BuildStatusText** (`TelegramService.cs:306`): replaced `catch { }` (swallowing
   OOM, ThreadAbort, etc.) with specific `catch (IOException)` / `catch (InvalidOperationException)`
   per A15.
3. **Reporter.GetRemoteUrl thread-safety** (`Reporter.cs:414-440`): static `_cachedRemoteUrl` and
   `_cachedRemoteRepo` fields were read/written without synchronisation. Now protected by a
   `System.Threading.Lock` with double-check under lock.
4. **WebhookNotifier unused import** (`WebhookNotifier.cs:1`): removed `using System.Net.Http.Json`
   (not used — the class builds `StringContent` manually).
5. **ProgressBar comment** (`Reporter.cs:391`): corrected `"20 chars wide"` to `"10 chars wide"`
   (matches the `const int width = 10`).

## Weak / shortcut / assumed — cannot fix this session

- **No mock-Telegram-server integration test.** The B6.1 gate spec ("mock-Telegram server test —
  push delivered; /status returns a status message") was not implemented. The 20 B6 tests are
  DTO/model/unit tests that never exercise the actual HTTP poll/send loop. The real Telegram
  integration has never been tested against the API. This is the largest gap: the service compiles
  and parses JSON correctly, but an integration-tested `IHostedService` would need a local
  mock server (e.g. `HttpListener`) that simulates `getUpdates` + `sendMessage` round-trips.
- **Shamshir acceptance is dry-run only.** No actual agent sessions were dispatched against
  the Shamshir codebase. The proof is that the driver can parse the conventions and generate
  prompts — not that sessions deliver P-0/P0.1 work. A real Shamshir run requires the actual
  repo + cTrader, which is out of scope for the Baton self-plan.
- **Fire-and-forget notify calls don't drain on shutdown.** `_ = telegram.PushAsync(...)` and
  `webhooks.FireAsync(...)` in `Orchestrator.Notify()` enqueue messages; if the host shuts down
  before the send queue drains, the last notification is lost. Acceptable for notification-loss
  semantics (the dashboard/report are the authoritative records), but a drain-on-shutdown in
  `TelegramService.StopAsync` would be more robust.
- **Telegram token is not validated at startup.** If `CONDUCTOR_TELEGRAM_TOKEN` points to an
  invalid bot token, the poll loop silently logs warnings (401 from `getUpdates`) but the
  service stays "configured." A startup liveness check (e.g. `getMe`) would fail-fast.
- **Inline keyboard is single-row.** All buttons appear on one horizontal row. Multi-row layout
  (dedicated rows for different action groups) would improve phone UX.
- **`EventLogTests.ReadAllSucceedsWhileLiveWriterHoldsTheFile` is flaky.** Timing-dependent test
  that polls an async writer for up to ~1s; occasionally times out on slow machines (passes on
  retry). Pre-existing, not a B6 regression.

## Risks for the next phase (B7 — Specialist personas)

1. **B7 consumes `ITelegramService`** — if it adds new push calls, the send queue must be
   validated for throughput (currently `UnboundedChannel`, fine for notifications but could
   grow if personas push high-frequency updates).
2. **B7 uses the same `IProgressProvider` + `RunState`** for its status screens — the
   `BuildStatusText` snapshot in TelegramService is a one-shot read; if B7 introduces
   persona-specific state, the status message must be extended.
3. **The clean-heartbeat guard** (`commitMessage?.StartsWith("chore(conductor):")`) is a
   string-prefix check — if B7 changes the heartbeat commit message format, heartbeats
   could leak commits again.
4. **The mock-Telegram-server gap** means any Telegram-breaking change in B7 won't be caught
   until a live run. Consider adding the mock integration test as a B7 or followup task.

## Concrete follow-ups (→ `.conductor/followups.md` tracked by B8)

1. **Add mock-Telegram-server integration test** — spin up an `HttpListener`, register the
