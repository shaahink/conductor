## 4 · Bug #32 — `doctor` exited 1 on seven checkpoints nothing could retire — FIXED

Commit `81d4981`, `src/Conductor.Core/TrackerGenerator.cs`.

Root cause, measured, not read off a comment. The tracker is **generated from** the work graph and
**read back as** the declared-work list:

- `TrackerGenerator.cs:109` re-emitted "stages in db but not in plan" as checkpoint **table rows**;
- `MarkdownTableProvider` parses **per line** with no section state, so the heading above a row is
  irrelevant — the rows were read straight back in as declarations;
- `WorkGraphSync.cs:84` tests `!declaredIds.Contains(item.TaskId)` **before** the out-of-plan test at
  `:85`, so an item the declared source still declares is never retired.

The generator therefore re-declared the orphans to the reader that fed the generator, `:85` was
unreachable, and W1.2's own stated contract ("their stage left the plan") could never fire.
`doctor`'s failing check is `DoctorCommand.CheckWorkCoverage` (`DoctorCommand.cs:350`, message at
`:364`) and it reads the declared source, not `run.db` — which is why deleting
`plans/karvan/.removed-face-items.json` did nothing. That file has exactly one reference in the repo
(`.conductor/followups.md:462`) and was never an input.

Fix: out-of-plan work is **listed** under `### Not in the plan`, never re-emitted as rows. A bullet
cannot match the row regex, which anchors on `|`. Visibility is kept; the section empties itself once
the next sync retires what it names. Deliberately *not* fixed by relaxing the archive predicate: an
archived item that is still declared gets **revived** (`WorkGraphSync.cs:73`), so that route
oscillates instead of converging.

```
$ dotnet test --filter FullyQualifiedName~K7OrphanBoardTests     # with the fix
Passed!  - Failed: 0, Passed: 2
$ git stash push -- src/Conductor.Core/TrackerGenerator.cs && dotnet test --filter ...K7OrphanBoardTests
Failed!  - Failed: 2, Passed: 0
```

The second test drives the real components end to end: doctor `fail` → sync → sync → the orphan is
archived, the view no longer mentions it, doctor `ok`, and a third sync is a no-op rather than an
archive/revive loop.

**What the owner will see.** The live board clears on its own, in two steps, and neither is a manual
edit: `Sync` only regenerates the view when something changed (`WorkGraphSync.cs:118`) and the board
is at equilibrium now, so (a) the first checkpoint claim under the new engine regenerates the tracker
through `ControlPlaneServer.Tasks.cs:103`, and (b) the next sync archives the seven rows. Until then
`doctor` still exits 1 on them.

## 5 · Bug #33 — the reinstall resumed from a stale snapshot, in silence — FIXED

`src/Conductor.Core/Store/StateMigration.cs`, `StateHome.cs`, `Program.cs`.

The import fired once (`if (File.Exists(targetDb)) return null;`, old `StateMigration.cs:48`) and an
existing target was never reconsidered. That is exactly wrong for an upgrade: a new build resolves
state once and leaves a snapshot, the **published** engine goes on driving the same run against
`<repo>/.conductor/run.db` for hours, and the install then makes the snapshot live. The run resumes
from where it stood at that first resolution and every session since is missing from its own history.

The second half of the fix is the one that was easy to miss: `StateHome.cs:143` short-circuited with
`!File.Exists(target)`, so `ImportLegacy` was never called once a target existed — changing
`StateMigration` alone would have been dead code.

New rule, and it is asked of **content**, not of timestamps. `SqliteRunStore.CompareHistories` reads
the session keys and event keys out of both files and returns `Same` / `SourceAhead` / `CopyAhead` /
`Diverged`. A copy whose history is a subset of the source's is **refreshed** (nothing is in it that
is not also in the source); a copy holding history of its own is **never touched** and the divergence
goes to stderr through the new `StateMigration.Warn` sink; `Same` and `CopyAhead` — the ordinary
states, the second of them being every day after the install — are silent. A refresh also deletes
target sidecars the new source lacks, since a fresh main file beside a stale `-wal` is a torn database.

Four things were measured on the way here, and each one killed a simpler design:

1. **Size and mtime cannot answer this.** Look at the database driving this very run, at the moment of
   the proof: `run.db` 4,755,456 bytes last written **10:57:34**, `run.db-wal` 4,260,112 bytes last
   written **11:50:19**. Every event of this session is in the `-wal`; the main file has not moved.
   Windows also does not refresh a sidecar's write time while its handle is open.
2. **Reading a WAL database read-only creates a `-shm` beside it**, so a content probe run before a
   file-level check makes the file it just read look written-to. Every `FileInfo` fact is now taken
   before either database is opened.
3. **Sessions are not in the event log** — `RecordSession` INSERTs straight into `sessions`
   (`SqliteRunStore.Sessions.cs:74`) with no event — so comparing event logs alone misses session
   history entirely.
4. **Comparing sizes is wrong even so.** Two databases that share an ancestor and are then both
   written assign the SAME next session number and the SAME next per-run `seq` to DIFFERENT work, so
   counts, `MAX(number)` and tip-identity all call a diverged copy a prefix and overwrite work that
   exists nowhere else. Hence set difference.

```
$ dotnet test --filter "FullyQualifiedName~K7_2StaleSnapshotTests|FullyQualifiedName~K3_1StateHomeTests"
Passed!  - Failed: 0, Passed: 30
```

Seven new tests. Five are file-level, exercising the fallback fence for a file that is not a database
at all (refresh-and-say-so, never-clobber-plus-warn, unmoved-source-is-a-no-op, no-receipt-is
untouchable, sidecars cleared). Two run in real SQLite through the real `StateHome.Resolve`:
`Resolve_RefreshesACopyTheLegacyDatabaseHasOutrun` (a session recorded to the legacy database *after*
the first resolution is present after the second) and `Resolve_NeverRefreshesADivergedCopy_AndSaysSo`
(both files gain exactly one session, so the two histories are the same LENGTH — only set difference
tells them apart, and session 50 survives). K3.1's own idempotence tests, including
`Resolve_IsIdempotent_AndNeverOverwritesPostImportWork`, are untouched and green.

**Live, through the real binary** — `.conductor/evidence/K7/K7.2-stale-snapshot-live.txt`, a scratch
rig in `TEMP` with its own plan and its own `CONDUCTOR_STATE_HOME`, driven by
`src/Conductor/bin/Debug/net10.0/conductor.exe`:

```
1. state home empty  -> conductor: imported existing run history -> ...\home\runs\...\run.db
2. same main file re-copied (same history) -> nothing on stderr, receipt still refreshed=false
3. the -wal copied too (source genuinely ahead)
   -> conductor: refreshed a stale copy of the run history -> ... 3 file(s) ...
      receipt: "refreshed": true
```

Two test classes now share an xUnit collection (`tests/Conductor.Tests/StateSinkCollection.cs`):
`Announce`/`Warn` are process-wide statics and xUnit runs classes in parallel, so one class's
`finally { Warn = null; }` was landing between the other's call and its assertion.
