## 1. The version gate, rehearsed against a real tag

The K7.2 acceptance ends with "the installed `conductor version --short` matches the releases page".
Nobody had produced that string. Reading `MinVerTagPrefix` off a line is not the same as tagging and
looking, so this tags and looks.

Rig: a `--no-hardlinks` clone of this repo in `%TEMP%\karvan-ship-rehearsal`, its own git dir, its own
output directory. **No tag was created in `C:/code/conductor` and nothing was installed** —
`tools/install.ps1` is the owner's to run at K7.2, and this reproduces only its build step
(`install.ps1:73` is `dotnet publish src\Conductor\Conductor.csproj -c $Config -o $InstallDir`).

```
git clone --local --no-hardlinks C:\code\conductor %TEMP%\karvan-ship-rehearsal
git -C <rig> tag v0.4.0                     # on b56d457, the tip of feat/karvan
git -C <rig> describe --tags                -> v0.4.0
git -C <rig> status --porcelain -uno        -> (empty: clean tree, so no .dirty suffix)
dotnet publish <rig>\src\Conductor\Conductor.csproj -c Release -o %TEMP%\karvan-ship-out
```

```
> conductor version --short
0.4.0+b56d457ac0e2

> conductor version
conductor 0.4.0+b56d457ac0e2
  commit   b56d457ac0e2
  built    2026-08-05T12:14:57Z
  runtime  .NET 10.0.9
  os       Microsoft Windows 10.0.26200
```

**Verdict: the gate passes, and the string the owner will compare is `0.4.0+<sha>`.** Not `v0.4.0`,
not a bare `0.4.0`, and — the failure this could have been — not `0.0.0-alpha.0`, which is what a
tagless checkout produces and what `release.yml` fetches at depth 0 to prevent.

The four links in that chain, each checked rather than assumed:

| link | where | what it does with `v0.4.0` |
|---|---|---|
| tag prefix | `src/BuildStamp.targets:25` | `MinVerTagPrefix` = `v`, so the tag is recognised and `$(Version)` is `0.4.0` |
| build metadata | `src/BuildStamp.targets:74-76` | `InformationalVersion` = `$(Version)+$(ConductorCommitSha)`, `.dirty` appended only for an unclean tree — absent here |
| release guard | `.github/workflows/release.yml:64` | `case v[0-9]*` matches, `version=0.4.0` |
| release body | `tools/changelog-section.sh 0.4.0` | run today, exit 0, extracts the `[0.4.0]` section |

And the consumer of that string: `conductor update` refuses to install a binary whose reported
version is not the release's (`UpdateCommand.cs:156`). `0.4.0+b56d457ac0e2` against tag `v0.4.0`
compares **equal** — `SemVer.TryParse` strips a leading `v` (`SemVer.cs:47`) and splits build
metadata off (`SemVer.cs:49-51`), and `CompareTo` never looks at it (`SemVer.cs:82`), pinned by
`SemVerTests.cs:79-80`. So the update path accepts the release this tag will produce.

## 3. The closure ledger's pin was checking the ledger against a copy of itself

`K7_1ClosureLedgerTests` says in its own summary that what it checks is "the *correspondence*: every
bug `run.db` still calls open must appear in the ledger". It did not. `OpenAtEraEnd` was a hardcoded
array of fourteen ids, and both tests compared the markdown to that array — so the pin could only
catch someone editing the table, never the table going stale. It was green today while three of its
fourteen rows were closed bugs.

Measured against the store (`SELECT * FROM bugs WHERE id >= 28`):

| bug | ledger said | `run.db` says |
|---|---|---|
| #28 | open, "K7.2, and it is not theoretical" | `fixed`, session 26 |
| #29 | open, "K7.2, with #28" | `fixed`, session 26 |
| #32 | open, "the owner" | `fixed`, session 27 |
| #33 | absent (filed after) | `fixed`, session 27 |
| #34 | absent (filed after) | `fixed`, session 28 |

`conductor bug list` reports **eleven** open: 15, 16, 17, 18, 19, 20, 21, 23, 24, 27, 31.

The stated reason for not reading `run.db` had also expired: it was "the repo-local copy is
half-migrated (bugs #28/#29)", and #28/#29 are the two that got fixed. Verified today —
`dotnet run --project src/Conductor -- doctor` reads that store through to `✓ state` instead of dying
at `MigrationRunner.cs:85`.

What changed:

- The ledger keeps all fourteen rows. Eleven stay in the open table with their owners; the five that
  closed move to a new **Bugs closed after this ledger was first written** table naming `run.db`'s own
  `fixed_session`. Nothing is deleted — deletion is the failure mode that reads as tidiness.
- `BugRows` now cuts a table at the next `### ` heading, so the second table's rows can never be
  counted as the first's (they would have read as open bugs with no owner).
- A new test, `EveryBugClosedAfterTheLedgerWasWrittenIsRestatedWithTheSessionThatClosedIt`, pins the
  closed table and requires a parseable session number in every row.
- The class summary no longer claims a correspondence check it does not do. The honest reason to pin
  ids as data is stated instead: **this ledger is a snapshot of an era's end**, and a test that read
  the live bug list would go red the day the next era filed its first bug.

## 4. One thing the owner should expect, and it is not a defect

`doctor` still fails one check on this repo and exits non-zero:

```
✗ work  work item(s) [F0.1, F1.1, F1.2, F2.1, F3.1, R0.1, R0.2] derive stages not in the plan (G13)
```

That is bug #32, fixed at session 27 and **not yet in effect here**. `doctor` reads declared work from
the generated tracker (`DoctorCommand.cs:353`), and the tracker is regenerated by the *running*
engine — which is the published one, from before the fix. The fix stops emitting those seven as table
rows (`TrackerGenerator.cs:109-130`, pinned by `K7OrphanBoardTests`). **The first regeneration by the
newly installed engine clears the rows and the check together.** If it is still red after the K7.2
reinstall, that is a real regression and this is the paragraph that says so.
