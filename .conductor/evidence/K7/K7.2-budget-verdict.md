# K7.2 part 3 — `conductor budget` stops contradicting itself on this run

Session 28, stage K7. K7.2 itself remains BLOCKED and owner-only; this is the same shape as parts 1
and 2 — a defect that fires *during the owner's ship*, found by measurement and closed before it
ships. Filed as bug **#34**, now fixed and closed.

## What was wrong

`conductor budget` is the flagship verb K4.2 shipped and the one the v0.4.0 release notes lead with
(`CHANGELOG.md:24-31`, "Its own score, produced by the tool this era shipped"). Run against this
repo's own run it gave an answer that contradicted itself in a single sentence.

`src/Conductor.Core/Budget/BudgetAnalyzer.cs:262` (pre-fix):

```csharp
var verdict = w.CapTokens is { } cur && SameCeiling(cur, cap)
    ? $"your budget is already where the measurements put it - {Millions(cap)} at {ratio…}, nudge {Millions(prescribedNudge)}."
    : $"set maxSessionTokens to …";
```

`SameCeiling` compares the **cap only**. A budget is a ceiling *and* a nudge, so a window whose cap
already matches but whose `softBreakRatio` does not was told nothing needed changing — while the same
sentence named a ratio it was not running and the `limits` block underneath differed from the live
config.

### Measured, verbatim, against this repo's `run.db`

Full capture: `K7.2-budget-verdict-before.txt` (fresh Debug build, `dotnet run --project src/Conductor
-- budget`, not the `conductor` on PATH — the published engine predates K4.2 and answers
`error: Unknown command 'budget'`).

```
1-27 32M / nudge 22.5M               25   365.5M   24    15.2M   3.27M      13.8M          0    1.86M (n=7)
now: cap 32M · nudge 22.5M (0.70) · nudge vs floor 6.90x · vs median closer 1.63x · headroom 9.46M
  > your budget is already where the measurements put it - 32M at 0.85, nudge 27.2M.
    "limits": { "maxSessionTokens": 32000000, "softBreakRatio":   0.85 }
```

The run is at **0.70 / nudge 22.5M**. The line above the verdict says so. The verdict says "already
where the measurements put it" and then names **0.85 / 27.2M**. An operator who reads the headline
does nothing; the block under it moves the nudge by 4.7M — **21%**.

That this is a defect and not a matter of taste is settled by the doc: `docs/dev/TOKEN-BUDGET-TUNING.md:272`
already writes the correct reading, reached by a human looking past the verdict — *"`conductor budget`'s
prescription for this run is **32M at 0.85** — the cap is where the measurements put it, and the ratio
could rise."* The doc was right and the tool's headline was not.

## The fix

`BudgetAnalyzer.cs:262-279` — the verdict is chosen on **both** halves of the config, with a third
branch for the case that actually fires here:

- cap matches **and** ratio matches → "already where the measurements put it" (unchanged).
- cap matches, ratio does not → *"the ceiling is right and the nudge is not: keep maxSessionTokens at
  X and move softBreakRatio A -> B - the nudge goes N -> M, which clears the … largest closer, …"*
- otherwise → "set maxSessionTokens to …" (unchanged).

`SameRatio` (`BudgetAnalyzer.cs:303`) compares at **half the 0.05 config grain**. Not exact equality:
`NudgeRatio` is the ratio the rail was *measured* firing at, which lands a little past the declared
one — sarban-face declared 0.75 and measured 0.76. Half a grain calls that the same and still calls a
genuine one-notch difference different.

## Proof the real case is fixed

Same command, same database, after the change (`K7.2-budget-verdict-after.txt`):

```
now: cap 32M · nudge 22.5M (0.70) · nudge vs floor 6.90x · vs median closer 1.63x · headroom 9.46M
  > the ceiling is right and the nudge is not: keep maxSessionTokens at 32M and move softBreakRatio
    0.7 -> 0.85 - the nudge goes 22.5M -> 27.2M, which clears the 26.1M largest closer, headroom 4.8M
    is 2.6x the measured 1.86M wrap-up.
```

The tool now says what the doc says. Nothing else in the output moved.

## Deliberately not done, and why

`CHANGELOG.md:28-29` and `docs/dev/TOKEN-BUDGET-TUNING.md:260` carry the K7.1 figures — **23
checkpoints / 14.1M / 22 sessions**. The same command now measures **24 / 15.2M / 25 sessions**
(above). They are not corrected here: they are labelled as the K7.1 re-measure, they are pinned by
`K7_1ClosureLedgerTests.cs:124`, and *any* figure written before the final session is stale by
construction — refreshing it every session is churn that can never converge. The owner regenerates at
tag time; it is in the handoff.

The prescription itself (32M → 0.85) is still **not** applied to `plans/karvan/core.plan.json`, for
the reason `TOKEN-BUDGET-TUNING.md:274-276` already gives: re-tuning the ceiling mid-run would change
the budget under the sessions running against it.
