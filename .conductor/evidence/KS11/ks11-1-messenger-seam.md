# KS11.1 — the messenger seam, and the proof it changed nothing

*Karvansara edge, stage KS11 (Chapar — the remote surface). Session #2, 2026-08-18.*

CHAPAR **CH-1**: message composition, chat profiles and evidence browsing become channel-agnostic
behind a messenger seam; `TelegramService` becomes the transport adapter behind it. No second
channel is built — a fake channel proves the seam for free.

The checkpoint's three falsifiable exits, each with what was measured.

---

## Exit 1 — current pushes are byte-identical through the seam

**Method.** The bytes were pinned BEFORE anything moved. `tests/Conductor.Tests/KS11_1SeamGoldenTests.cs`
drives fifteen cases through `RecordingBotApi` — the same stub K5.4 asserts against — and records the
whole call as `BotCall.Describe` renders it: the Bot API method, whether the push buzzed, what it
threaded onto, an uploaded file's name and byte count, and the full text after stamping and chunking.

The goldens were generated by the **pre-seam engine** and committed at `7e64866`, before a line of
`src/` was touched. The seam landed at `897e295`. The goldens were not regenerated, and they are not
regenerable by accident: a missing golden FAILS with its reason, and writing one needs
`CONDUCTOR_GOLDEN_REBASELINE=1` set deliberately.

**Cases (15).** Pushes — `push-plain`, `push-session-end`, `push-session-end-rollover`,
`push-run-complete`, `push-run-complete-skipped`, `push-evidence-batch` (six artifacts against the
four-file budget, so both the uploads and the text overflow are covered), `push-keyboard`. Commands —
`/status`, `/tasks`, `/start`, `/daily`, `/chat`, `/inject <text>`, `/pause`, `/abort`.

**Result.**

```
$ dotnet test Conductor.slnx --filter "FullyQualifiedName~KS11_1SeamGoldenTests" --no-build
Passed!  -  Failed: 0, Passed: 15, Skipped: 0, Total: 15

$ git diff --stat 7e64866..HEAD -- tests/Conductor.Tests/testdata/ks11
(no output — not one byte of any golden moved)
```

That second command is the claim. Fifteen goldens generated by the old code pass unchanged against
the new code; had the extraction altered a caption, a stamp, an anchor, a severity or a chunk
boundary, the file would have had to move and it did not.

**One asymmetry the goldens caught and preserved**, worth knowing before KS11.3 rewrites the
grammar: in an evidence batch the four uploads carry the ARTIFACT's session number (`s7`) while the
overflow message carries the LIVE counter (`s12`), because the overflow enqueues with `null`. That is
current behaviour, now pinned; it is not something this checkpoint introduced.

## Exit 2 — a fake channel drives the full surface

`tests/Conductor.Tests/KS11_1FakeChannelTests.cs` — 17 tests, no Telegram type in the file, no HTTP
listener, no hosted service, no long-poll. `FakeChannel : IMessageChannel` collects what it is given.

Driven through `RemoteSurface` directly: every push type; the fan-out proving one body becomes one
copy per configured chat; a dead channel dropping everything; the evidence budget (four attachments
then one text line); a missing artifact degrading to "not attached" instead of throwing inside a
fire-and-forget push; a keyboard suppressed where control is not wired; every read command; silence
on an unknown command, an empty message and ordinary chat; a control verb writing the control file
BEFORE it acknowledges; a destructive verb writing nothing until the button comes back; a cancelled
and an unconfirmed callback writing nothing; and the inject button arming a chat for exactly one
following plain message — a command typed while armed is still a command.

Before this seam, every one of those questions needed a listener impersonating api.telegram.org.

## Exit 3 — an architecture test forbids Telegram types outside the adapter

`tests/Conductor.Tests/KS11_1SeamBoundaryTests.cs`, three rules. Comments are stripped before
matching, exactly as `ArchitectureBoundaryTests` does it — a doc comment explaining why the seam does
NOT do something Telegram-shaped is the most valuable line on the page.

1. **`The_seam_contains_no_telegram_identifier_anywhere`** — zero allowlist, no mechanism for one.
   Every file under `src/Conductor.Core/Integrations/Messaging/` is free of `Telegram*` and `Tg[A-Z]*`.
   Making this true required moving two things OUT of the seam rather than excusing them:
   `TelegramLimits.cs` → `src/Conductor.Core/Integrations/TelegramLimits.cs`, and `HtmlChunker`'s
   `TelegramMaxChars` / `TelegramMaxCaptionChars` → `TelegramLimits.MaxMessageChars` /
   `MaxCaptionChars`. `HtmlChunker.Split` now takes its limit rather than defaulting to one
   messenger's.

2. **`No_seam_type_names_a_telegram_type_in_any_signature`** — the compiled truth, by reflection over
   every member of every type in the seam's namespace. A field typed `TelegramConfig` or a method
   returning a `TgUpdate` fails here even if the source hid it behind a `using` alias.

3. **`Only_the_declared_adapter_files_name_a_telegram_type`** — an exact set equality, not a
   containment check, so the list can only shrink: a NEW file naming a Telegram type fails, and a
   file that has been CLEANED also fails until it is struck off.

   Making rule 3 true meant the orchestration had to stop naming a messenger, so
   `ITelegramService` → **`IRunNotifier`**, `NoOpTelegramService` → `NoOpRunNotifier`,
   `MutedTelegramService` → `MutedRunNotifier`, `RunContext.Telegram` → `RunContext.Messenger`
   (37 files). `RunLoop`, `VerdictEngine`, `Orchestrator` and `RunContext` no longer name Telegram at
   all. Config and contract types keep their names and are asserted as a subset that must really
   still name one — `TelegramConfig` is a plan-file key and the DTOs are an HTTP contract.

   **The declared adapter, and the honest residue.** `TelegramService*.cs`, `TelegramReadiness.cs`,
   `TelegramLimits.cs`, `NoOpRunNotifier.cs` are transport. Three are not: `SecretsStore.cs` reads
   the bot token, `ParkNotifier.cs` wraps the notifier to mute it, and **`WatchRemote.cs` reaches for
   `TelegramService.ResolveToken` and `DefaultApiRoot` to send SF5.3's own push outside the run
   loop** — it has never been behind any seam, folding it in is later work, and rule 3's list is
   where that is recorded rather than forgotten.

## What moved

| From | To |
|---|---|
| `TelegramService.Messages.cs`, `.Context.cs` (composition, stamp, git facts) | `Messaging/MessageComposer.cs` + `MessageComposer.Views.cs` |
| `TelegramService.Commands.cs`, `.Callback.cs` (dispatch) | `Messaging/CommandRouter.cs` (decides) + `Messaging/RemoteSurface.cs` (acts) |
| the fan-out and the queue guards | `Messaging/IMessageChannel.cs` + `TelegramService.Channel.cs` |
| `BuildInlineKeyboard` (composition) | `TelegramService.Transport.cs`, where the wire format lives |
| `OutboundMessage.KeyboardJson` (pre-serialised Telegram JSON) | `OutboundMessage.Buttons` (`MessageButton`) |

`IMessageChannel` has **two** send verbs, not one, because the engine really has two paths and
collapsing them would not have been behaviour-preserving: `EnqueueAsync` fans a push onto the ordered
queue that survives the shutdown flush; `SendAsync` answers one chat now. A reply through the push
queue would arrive after the backlog; a push sent directly would lose its ordering and its flush.

## Two things the gates caught, fixed rather than relaxed

- The **ratchet gate** failed: `TelegramService.cs` at 502 lines and `MessageComposer.cs` at 538,
  both over the 500-line ceiling. Split by responsibility — `MessageComposer.Views.cs` (the pulled
  views) and `TelegramService.Channel.cs` (the channel implementation). The ceiling was not touched.
- A `MessageButton` overload of `BuildInlineKeyboard` was an `AmbiguousMatchException` at RUNTIME:
  `B6_1TelegramTests` reaches for that method by string through reflection. The seam's version is
  named `KeyboardFor` instead.

## Not in this checkpoint

`ChatProfile` and `ChatTarget` exist and every chat resolves as `Admin` — which is what every chat
IS today. Reading profiles from a plan, refusing an unknown profile string by name, and the closed
observer surface with its exhaustive command-by-profile matrix are **KS11.2**. One thing KS11.2 must
know: `RemoteSurface.HandleCallbackAsync` answers whoever PRESSED a button, not the chat the keyboard
was posted in, so the profile has to be resolved for the destination.
