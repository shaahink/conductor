# KS11.3 — onboarding, and the push grammar

*Evidence for `KS11.3`, karvansara-edge stage KS11 (Chapar — the remote surface). Session #3,
2026-08-18. Spec: `docs/dev/CHAPAR-REMOTE-SURFACE-2026-08-18.md`, decisions CH-4 and CH-5.*

Three exits, declared in the ledger before any edit. Each is below with the artifact that shows it.

---

## Exit 1 — onboarding, per profile, at run start and on `/start`

**What it says.** CH-4's three questions, in the chat's own voice. Composed by
`MessageComposer.OnboardingAsync(profile, twoWay)`
(`src/Conductor.Core/Integrations/Messaging/MessageComposer.Grammar.cs:23`), from the templates
`NotifyDefaults.OnboardingAdmin` / `OnboardingObserver` — so an owner can override either one at
`<templatesDir>/notify/onboarding-admin.md`, the same way every other push is overridable.

The observer's, pinned at `tests/Conductor.Tests/testdata/ks11-3/onboarding-observer.txt`:

```
<b>Karvansara edge</b> — this chat is now following a conductor run.
An agent is working through a plan on its own; this is where it reports.
2 stages: KS11 → KS12 · 2/4 checkpoints done
<code>budget $42.00 of $50.00 (84%, $8.00 left) · tokens 3.5M</code>
<b>What arrives here</b>
A message when a session ends, when evidence lands, and when the run finishes or parks for a
decision. Each one says what landed, what proves it, and what it has cost so far. Nothing is
filtered — this is the same story the run's owner gets.
<b>What you can ask</b>
/status, /tasks, /daily — reading only. Nothing this chat types can move the run.
```

The admin's (`onboarding-admin.txt`) differs in exactly the two places it should: *"the control
surface for a conductor run"*, and an ask line that carries `/inject` and the control verbs — or,
when `enableTwoWay` is off, says so and names the setting that turns it on.

**The list is never written twice.** `SurfaceCommands.AskLine(profile, twoWay)`
(`SurfaceCommands.cs:79`) builds the "what you can ask" line from the SAME catalogue KS11.2's gate
enforces. `What_an_observer_is_offered_is_what_the_gate_actually_allows` walks every verb the
message offers back through `CommandRouter.Route` and asserts it answers — and that no verb outside
the browse scope appears in the message at all. A promise that drifts from the permission fails the
build.

`SurfaceCommands.BrowseList` was also narrowed to verbs that are actually IMPLEMENTED. It used to
include `/progress`, `/evidence`, `/money` and `/tokens`, which have no handler until KS11.4 and
KS11.5 — offering them would be a bot that ignores the reader the first time they take it at its
word. The list grows by itself as the flags flip.

**When it is sent.**

| moment | wiring |
|---|---|
| run start | `RunLoop.NotifyRunStart` → `IRunNotifier.PushOnboardingAsync` (`RunLoop.Plumbing.cs:249`), before the run's first word, and behind the same `AllowOneOff()` dry-run guard every other push respects |
| a chat added mid-run | `TelegramService.ApplyPlanAsync` calls it after a live plan reload (`TelegramService.Lifecycle.cs:107`) — the case CH-4 actually names |
| `/start` | `SurfaceAction.Onboard` → `RemoteSurface.ForceOnboardAsync`, which re-sends on request and leaves by `ReplyAsync`, the door every other answer to a typed command uses |

Idempotent per chat (`RemoteSurface._onboarded`), so the first two can both be called
unconditionally and only a chat that has not been told hears anything.

`IRunNotifier.PushOnboardingAsync` is declared with a **default implementation** returning
`Task.CompletedTask` — a notifier that reaches nobody has nobody to introduce, and no existing
implementer had to change.

## Exit 2 — the push grammar: headline / proof / telemetry

`NotifyDefaults.SessionEnd` is now:

```
<b>{outcome}</b>{duration}      headline — what happened
{landed}                        what landed — commits, checkpoints claimed
{result}                        the session's own words (K5.1 contract)
{proof}                         what shows it
{telemetry}                     the numbers, in monospace
{report}
```

Before and after, from the rebaselined golden `testdata/ks11/push-session-end.txt`:

```diff
-    progress: 1/4 checkpoints · KS11 1/4
-    gates: build:OK gates:6/6
-    evidence: .conductor/evidence/KS11/ks11-1-seam.md
-    cost: $1.25 · run $42.00 of $50.00 (84%, $8.00 left) · score 88/100
+    proof: gates build:OK gates:6/6 · evidence .conductor/evidence/KS11/ks11-1-seam.md
+    <code>progress: 1/4 checkpoints · KS11 1/4 · cost: $1.25 · run $42.00 of $50.00 (84%, $8.00 left) · score 88/100</code>
```

The artifact used to be the last line of the result block, below the gaps, where it read as an
afterthought rather than as the thing that makes the headline checkable. It is now half the proof
line, beside the gate verdict (`ProofLine`, `MessageComposer.Grammar.cs:86`).

**Tokens.** `RunState.TotalTokens` (`RunState.cs:214`) is new and is the one place that decides what
"tokens" means: `SessionRecord.TokensTotal`'s own definition, **cache reads included**. The three
totals that predate it (`TotalTokensInput/Output/Reasoning`) exclude cache reads — about 98% of what
an era like this one spends — so a telemetry line built from those would have reported a fiftieth of
the truth. `The_token_figure_counts_cache_reads` pins both numbers on the same fixture: 3,500,000
against 60,000.

**Nothing breaks for an owner with a template.** The K5.4 facts `progress`, `gates` and `cost` are
still supplied to `session-end`, `run-complete` and `evidence`, so an override written against the
old shape renders instead of being refused. Only the built-in changed.

**One behaviour change beyond composition:** a confirmation keyboard now goes only to Admin targets
(`RemoteSurface.PushWithKeyboardAsync`). KS11.2 closed the callback an observer could press; this
stops the button being offered at all. The observer still gets the news — the text half rides
`PushAsync`.

## Exit 3 — goldens pin both profiles, and a checkpoint push reads standalone

**Two golden sets, pinning different things.**

- `testdata/ks11/` (KS11.1's) pin the WIRE — the real `TelegramService`, the real Bot API stub,
  every field a call carried. **Six of the fifteen moved**, in a rebaseline that is readable in the
  commit: `push-session-end`, `push-session-end-rollover`, `push-run-complete`,
  `push-run-complete-skipped`, `push-evidence-batch`, `cmd-start`. The other nine did **not** move —
  `cmd-status`, `cmd-tasks`, `cmd-daily`, `cmd-chat`, `cmd-inject`, `cmd-pause`, `cmd-abort`,
  `push-plain`, `push-keyboard` — which is the measurement that the admin command surface is
  untouched except `/start`, which CH-4 replaces on purpose.
- `testdata/ks11-3/` (new, nine files) pin the TEXT, per profile, through the fake channel:
  `onboarding-admin`, `onboarding-observer`, `push-session-end`, `push-session-end-rollover`,
  `push-run-complete`, `push-evidence`, and the three observer refusals
  (`cmd-pause-observer`, `cmd-inject-observer`, `cmd-chat-observer`). Strict: a missing golden
  FAILS rather than being written, and `CONDUCTOR_GOLDEN_REBASELINE=1` is the deliberate way to move
  one.

**Do both profiles get the same story?** Measured, not assumed:
`Both_profiles_receive_the_same_story` fans a session-end push to an admin chat and an observer chat
and asserts the two bodies are equal byte for byte. That is CH-3's design — an observer gets the
run's whole story and only what they may ASK is closed — and a "filtered for the stakeholder"
version would be a second thing to maintain and a second thing to be wrong.

**A checkpoint push reads standalone** — `A_checkpoint_push_reads_standalone` takes ONE composed
body, with no other message for context, and asserts each of the three answers is present and on
its own line:

| question | asserted |
|---|---|
| what landed | `<b>Advanced</b>` opens it; a `landed:` line names `claimed KS11.3` |
| what proves it | exactly one `proof:` line, carrying `gates build:OK gates:9/9` **and** `evidence .conductor/evidence/KS11/KS11.3-grammar.md` |
| what it cost | exactly one `<code>…</code>` line, carrying progress, `cost: $1.25 · run $42.00 of $50.00 (84%, $8.00 left)`, and `tokens 3.5M` |

## On the wire, through the real adapter

The goldens above pin what the composer writes. `KS11_3OnWireTests` drives the real
`TelegramService` against `RecordingBotApi` with two chats of different profiles configured in the
plan — so profile resolution, the send queue, the identity stamp and the per-chat fan-out are all
the engine's own:

- `Each_chat_is_introduced_in_its_own_voice_and_only_once` — two calls, two chats; the admin's
  carries `/inject`, the observer's carries neither `/inject` nor `/abort`; a second
  `PushOnboardingAsync` adds nothing.
- `An_observer_control_attempt_is_refused_on_the_wire` — `/abort` typed in the observer chat, driven
  through the stub's own long-poll: one named refusal returns to THAT chat, and `control.json` was
  never written.
- `The_admin_chat_on_the_same_plan_still_gets_the_keyboard` — the same plan, the same verb, from the
  admin chat: `Confirm abort?`. The refusal is a profile decision, not the control surface going away.
- `A_session_end_push_carries_its_telemetry_in_monospace` — money and tokens on one `<code>` line.

`BotCall` gained a `ChatId` field to make these assertions possible. It is deliberately absent from
`BotCall.Describe()`, so no golden had to move to give the tests a chat id.

**Scratch only**, per this stage's live-proof rule: a scratch token (`111111:scratch-bot-token`), the
stub standing at `TelegramConfig.ApiBaseUrl`, chat ids that reach nothing. No proof in this
checkpoint touched a real bot.

## What KS11.3 deliberately did not do

There is no per-checkpoint push in this engine — checkpoint transitions ride inside the session-end
push's `NewlyDone` list, and nothing pushes on a checkpoint flipping DONE. "A checkpoint push reads
standalone" is therefore read as, and proven against, the session-end push. Adding a genuine
per-checkpoint push would be new behaviour this checkpoint was not asked for.
