## Exit 1 — the config shape, and one place that resolves it

`telegram.chats` is a list of `{ chatId, profile }`. Resolution happens in exactly one function,
`TelegramConfig.ResolvedChats()` (`src/Conductor.Core/Models/TelegramConfig.cs:33`), and the adapter
turns its output into `ChatTarget`s in one more,
`TelegramService.ResolveTargets` (`src/Conductor.Core/Integrations/TelegramService.Channel.cs:32`).

```jsonc
"telegram": {
  "chats": [
    { "chatId": "99205495",   "profile": "admin"    },
    { "chatId": "-100123456", "profile": "observer" }
  ]
}
```

Order is: the `chats` block as written, then any `allowedChatIds` entry it did not name, as admin.

Pinned by `KS11_2ChatProfileConfigTests.The_chats_block_parses_from_plan_json_and_carries_its_profiles`
(parsed from JSON, not a hand-built model — the thing that breaks silently is the key name) and
`.The_chats_block_wins_for_ids_it_names_and_the_rest_stay_admin`.

## Exit 2 — back-compat is byte-identical, and the pin is the pre-seam goldens

The fifteen KS11.1 goldens under `tests/Conductor.Tests/testdata/ks11/` were generated at `7e64866`
by an engine that had never heard of a profile, from a plan carrying only `allowedChatIds`. They are
never regenerated, so they ARE the back-compat measurement. They pass unchanged:

```
dotnet test --filter "FullyQualifiedName~KS11"     → Failed: 0
dotnet test --filter <every suite touched>          → Failed: 0, Passed: 659, Duration 32 s
```

(suites: KS11*, Telegram*, Architecture*, Plan*, Doctor*, ControlPlane*, SF7_1*, SC1*, Notif*)

Below the goldens, at the level they cannot see:

- `An_old_shape_plan_resolves_to_its_own_ids_in_order_all_admin` — the resolved target list is the
  plan's own ids, in the plan's own order, every one `Admin`.
- `A_plan_with_neither_block_serves_nobody` — silent, as today.
- `An_admin_is_refused_nothing_and_routes_exactly_as_before` — the whole catalogue x `twoWay`
  on/off, with the expected action written out per verb. `Refuse` is a shape an admin can never see.

**Readiness was a real break, found and fixed.** Every status/readiness path counted
`AllowedChatIds.Count`, so a plan configuring its chats the new way reported *"push-only to
nobody"* while delivering perfectly. All five call sites now read `TelegramConfig.ChatCount`
(`TelegramConfig.cs:54`; sites in `TelegramService.cs:167`, `TelegramService.Lifecycle.cs:34,116`,
`DoctorCommand.cs:454,458`, `ControlPlaneServer.Telegram.cs:84`). `SameBlock`
(`TelegramService.Lifecycle.cs:124`) now compares resolved targets too, so a live plan edit that
demotes an admin chat is no longer read as "nothing changed" by the running loops.

## Exit 3 — an unknown profile is refused by name, at plan load

`TelegramConfig.ProfileRefusal()` (`TelegramConfig.cs:62`) in the shape `GithubConfig.BoardRefusal`
established, wired into `PlanConfig.CollectErrors()` (`PlanConfig.cs:355`). Never a default: a
profile the engine cannot read is a chat whose permissions the author does not know, and the failure
mode of guessing is handing an outsider the steering wheel.

**Driven live through the fresh build** (`dotnet run --project src/Conductor`, not the `conductor` on
PATH), against a scratch plan under `%TEMP%\ks11-2-rig` with its own state dir:

```
$ dotnet run --no-build --project src/Conductor -- status -p %TEMP%\ks11-2-rig\bad.plan.json
error: Invalid plan config:
  - telegram.chats entry '-100999888' has profile 'viewer', which is not a profile.
    it is 'admin' or 'observer'.
                                                                              (exit 1)
```

The same plan with `"observer"` loads, and doctor counts the chat that exists ONLY in the new block —
which is exit 2's readiness fix, proven live:

```
$ dotnet run --no-build --project src/Conductor -- doctor -p %TEMP%\ks11-2-rig\good.plan.json
> ✓ telegram token present, 1 allowed chat id(s)
```

Also pinned by `An_unknown_profile_fails_plan_load_by_name` (through the real `PlanConfig.Load` on a
real file), `The_same_plan_with_a_known_profile_loads`, and the theory
`Profile_strings_are_read_or_refused_but_never_guessed` — case and surrounding space are fine, an
empty string is refused, `owner` is refused by name, and a refused config resolves to **no targets**
rather than to a chat quietly promoted to admin.

## Exit 4 — the command-by-profile matrix is exhaustive, and that is falsifiable

CH-3 is enforced in ONE place: `CommandRouter.Gate` (`CommandRouter.cs`), which every inbound path
passes through before anything else — a typed verb, a plain message while injection is armed, and a
button press.

The surface is a LIST, not a set of samples:
`SurfaceCommands.All` (`src/Conductor.Core/Integrations/Messaging/SurfaceCommands.cs:45`) names all
16 verbs with a scope (Browse / Steer / Control). `KS11_2CommandMatrixTests` walks the whole list
against both profiles:

| test | what it walks |
|---|---|
| `Every_command_answered_for_an_observer_is_a_browse_command` | all 16 verbs; non-browse must be `Refuse` **and** the refusal must name the verb |
| `No_observer_input_of_any_shape_reaches_control_or_injection` | 16 verbs x 3 spellings x twoWay x armed = 192 inputs, plus plain prose armed/unarmed; none may yield Control/ConfirmControl/Inject/ArmInjection |
| `An_admin_is_refused_nothing_and_routes_exactly_as_before` | all 16 verbs x twoWay, expected action written per verb |
| `No_button_press_from_an_observer_chat_does_anything` | all six callback payload shapes |
| `An_unknown_command_from_an_observer_is_met_with_silence` | unknown slash, `@otherbot` form, plain text |

**"Exhaustive" is enforced, not claimed.** `Every_command_literal_in_the_router_is_in_the_catalogue`
scans `CommandRouter.cs` (comments stripped) for every slash literal it compares against and fails if
one is missing from the catalogue — so a verb added to the router without a decision about who may
use it fails the build rather than defaulting open. `Every_implemented_catalogue_entry_is_actually_in_the_router`
is the ratchet the other way.

**End to end through a channel**, not just the decision:
`An_observer_abort_leaves_one_refusal_on_the_wire_and_no_control_file` — an observer types `/abort`
and taps the confirm button; two named refusals leave the channel and `writeControl` is never
called, which is the fact that matters since the control file is what the engine obeys.
`An_observer_asking_status_gets_the_run_status` is the other half: a closed surface that answered
nothing would pass every test above and be useless.

### A hole this checkpoint found and closed

`CommandRouter.RouteCallback(data)` took **no profile at all**. Pushes fan out to every configured
chat, so a confirmation keyboard raised by the owner lands in the observer's chat too — pressing it
wrote `control.json`. It now takes the profile, and nothing on the callback surface is a browse verb,
so an observer is refused the whole of it by name.

### Falsifiability — measured, not asserted

The gate was removed (both call sites) and the matrix re-run:

```
Failed  No_button_press_from_an_observer_chat_does_anything (all 6 payloads)
Failed  Every_command_answered_for_an_observer_is_a_browse_command
Failed  No_observer_input_of_any_shape_reaches_control_or_injection
Failed! - Failed: 8, Passed: 6, Total: 14
```

The mutation was reverted immediately (`git diff --stat` back to 52 insertions, the real change) and
the suite re-run green.

## Documentation (CH-3 makes it part of this checkpoint)

- `docs/plan-config.md` — the `chats` key, and a **Chat profiles** table: what each profile may ask,
  what it never may, the jsonc example, and the honest caveat that evidence is served as-is.
- `docs/operating.md` — *"Letting someone else watch — a group chat with an observer profile"*: the
  three group-chat mechanics CH-3 names. Telegram privacy mode (leave it ON; `/status@yourbot`
  always reaches the bot, plain `/status` in a group may not), the `-100` supergroup id prefix, and
  that granting `observer` to a group is a decision about what that group may see.

`SF7_1DocsMatchRealityTests` — the gate that caught `telegram.chats` being undocumented — is green.

## What KS11.2 deliberately did not do

`/progress`, `/evidence`, `/money` and `/tokens` are in CH-3's observer set and in the catalogue, but
have no handler until KS11.4/KS11.5. They carry `Implemented: false`, and both profiles get today's
behaviour for them — silence. The matrix asserts an observer is never *refused* a browse verb, so
flipping the flag when the handler lands is the only change those checkpoints need here.
