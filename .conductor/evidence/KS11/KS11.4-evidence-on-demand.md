# KS11.4 — Evidence on demand

*Session 4 of the Karvansara edge run, 2026-08-18. Commits `df5048e` (feature + tests) and
`cb84b1e` (the six-golden rebaseline). Spec: `docs/dev/CHAPAR-REMOTE-SURFACE-2026-08-18.md`, CH-6.*

The tracker row's exit, restated: *`/evidence` lists checkpoints with evidence, `/evidence` with an
id sends the artifact (document upload for files, chunked text otherwise) with size caps and a
per-chat rate limit; an observer pulls a real evidence artifact end-to-end in the rig; the clip
constants no longer bound what a reader can reach.* Each clause is measured below.

---

## 1. The list — `/evidence`

`MessageComposer.EvidenceListText()` — `src/Conductor.Core/Integrations/Messaging/MessageComposer.Evidence.cs:41`.
Reads the tracker through `IProgressProvider` (the same read `/status` uses), keeps the rows whose
evidence cell names at least one path, and prints each artifact with its size — or with *not on this
machine* when the path no longer resolves, which is the case a list that hid it would turn into a
reader asking for something that cannot arrive.

Measured by `KS11_4EvidenceOnDemandTests`:

* `The_list_names_every_checkpoint_that_has_an_artifact_and_says_which_one_has_gone` — a rig whose
  tracker has four rows: one artifact, two artifacts under one claim, one row with the table's `-`
  placeholder, and one whose file was never written. The list names the first three artifacts with
  their byte counts, names the missing one as missing, and does not mention the row that has none.
* `The_list_is_not_bounded_by_the_push_side_line_budget` — thirty claims, thirty artifacts, all
  thirty in the answer. `EvidenceLinesPerPush = 8` (`MessageComposer.cs:283`) bounds a push nobody
  asked for; a reader who typed the verb asked, and the transport's chunker is what makes a long
  answer deliverable rather than a 400.

## 2. The pull — `/evidence <id>`

`MessageComposer.EvidenceFor(id)` → `AnswerFor(...)` — `MessageComposer.Evidence.cs:94` and `:118`.
The router turns the verb into a decision (`CommandRouter.cs:124–134`); the effect belongs to
`RemoteSurface.SendEvidenceAsync` (`RemoteSurface.cs:284`), which is what touches the disk, charges
the budget and puts the file on the wire.

* A resolved file leaves as an upload — `sendPhoto` when the artifact is visual, `sendDocument`
  otherwise, decided by `EvidenceKinds.IsVisual` exactly as the push path decides it.
  `An_artifact_arrives_as_an_upload_and_a_photo_when_it_is_visual` pulls a claim naming two
  artifacts and gets both, the `.png` as a photo and the `.md` as a document.
* Every way a pull can fail to produce a file SAYS which way it was —
  `A_pull_that_cannot_send_a_file_says_why`: an id nobody claimed, a row with no artifact yet
  (with its status), a path that no longer resolves. "Nothing arrived" is the failure this
  checkpoint exists to end, so silence is never the answer.

### The argument is an id, never a path

The security property of the whole verb. The reader names a checkpoint; the path comes from the
tracker row the engine itself wrote. `A_reader_cannot_ask_for_a_path_only_for_a_checkpoint` types
`../../../secrets.txt`, `/etc/passwd`, `C:\Windows\win.ini` and the true relative path of a real
artifact in the rig — all four are answered *No checkpoint …* with no attachment.

## 3. The caps — both the surface's own, neither Telegram's

| Cap | Value | Where | Why it is not the messenger's |
|---|---|---|---|
| Pulled artifact size | 10 MB | `MessageComposer.Evidence.cs:183` | Telegram would carry 50 MB. How much of the engine's disk a chat message may pull over the network is a decision of the surface, so a second channel inherits it. |
| Pulls per chat | 8 per 10 min | `:192`, `:194` | An upload is bytes off the engine's machine while the run is doing something else. |

* `An_artifact_over_the_pull_cap_is_named_rather_than_sent` — a file one byte over the cap is named
  with its size and its path instead of being uploaded.
* `A_chat_that_pulls_past_its_budget_is_refused_with_a_time_to_ask_again` — eight uploads, then a
  refusal that says when. A rate limit that answers "no" without answering "when" reads as the
  feature being broken.
* `One_chat_exhausting_its_budget_leaves_the_other_chat_alone` — the limit is per CHAT, so the group
  reader working through the artifact list cannot lock the owner out of their own run.
* `Listing_and_missing_ids_cost_nothing_only_uploads_do` — twenty lists and twenty mistyped ids
  later, the next real pull still arrives. Only an answer carrying a file is charged
  (`EvidenceAnswer.CostsBudget`), because charging for a typo is how a reader loses the artifact
  they were reaching for.
* `The_window_reopens_one_slot_at_a_time_as_the_oldest_take_falls_out` — `PullRateLimiter` takes its
  clock as an argument, so the half a test cannot observe by hammering the surface (the window
  REOPENING, one slot at a time) is asserted without a test that sleeps.

## 4. An observer pulls a real artifact end-to-end — `KS11_4OnWireTests`

Nothing is handed in. A real `TelegramService` resolves the observer profile from the plan, a real
long-poll delivers the command, the real dispatch routes it, and the real upload path reads the file.
The only double is `RecordingBotApi` standing at `TelegramConfig.ApiBaseUrl` — scratch token written
to the rig's own `.conductor/`, scratch chat ids, no real bot touched.

`An_observer_pulls_a_real_artifact_end_to_end` asserts the wire call itself:

```
method     sendDocument
chat       -100123456        (the observer chat, the one that asked)
field      document
file       seam.md, 900 B
caption    KS11.1 — the messenger seam · .conductor/evidence/KS11/seam.md
```

`A_mistyped_id_is_answered_on_the_wire_rather_than_ignored` pins the other half: an unknown id comes
back as a `sendMessage` to that chat, not as silence.

## 5. The clip constants no longer bound what a reader can reach

`What_the_push_budget_could_only_announce_is_pulled_whole` is the measurement. One batch of six
artifacts is pushed through the real service:

* four arrive as `sendDocument` — that is `EvidenceFilesPerPush = 4` (`MessageComposer.cs:281`);
* the fifth and sixth arrive only as text in the overflow message. The test asserts explicitly that
  no call carried `note-5.md` as a file;
* the observer then types `/evidence KS11.5`, and `note-5.md` arrives — 105 bytes, `sendDocument`,
  in the observer's chat.

Before this checkpoint that was unreachable from any chat by anybody. Honest scope: the two
constants that bound EVIDENCE (`EvidenceFilesPerPush = 4`, `EvidenceLinesPerPush = 8`) are answered
by a pull tier that reaches past both. The other two (`ResultMaxChars = 900` at `:349`,
`CommitLinksPerPush = 3` at `:321`) bound a session-end push's PROSE, not its evidence; nothing in
CH-3's closed command set reaches them, and neither the spec nor this row asks for a verb that does.
That is stated here rather than quietly counted as done.

## 6. What moved elsewhere, and what did not

* `SurfaceCommands.cs:52` — `/evidence` flips to `Implemented`. That single flag is what puts the
  verb in `BrowseList`, in both profiles' onboarding ask-line, and in the observer refusal;
  KS11.3 built it that way so a chat is never promised a verb that answers silence.
  Six goldens move as a result, each by the same clause, in their own commit `cb84b1e`. The nine
  wire goldens that pin the admin push surface are byte-identical.
* `docs/operating.md` — CH-6's honest caveat, in docs rather than in code: evidence is served as-is,
  and since KS11.4 an observer group can pull the run's whole evidence trail rather than only the
  files a push carried. Granting the profile is that decision.

### A test-suite defect found and fixed on the way

`KS11_3OnWireTests` set `CONDUCTOR_TELEGRAM_TOKEN` in the **process** environment. xUnit runs test
classes in parallel, so that token is visible to every other test in the assembly — and three of
them assert what a run with NO token says. They went red the moment a second wire rig widened the
window (`DoctorCommandTests.CheckTelegram_Warn_WhenConfiguredButNoToken`,
`ControlPlaneServerTelegramTests.GetTelegramStatus_Configured_ButNoToken`,
`SC1TelegramLateConfigTests.PostTelegramToken_SaysWhatIsStillMissing_WhenTheTokenAloneIsNotEnough`).
Both wire rigs now write the token into their own scratch `.conductor/`, which is what the KS11.1
golden rig already did. Measured, not theorised: the failure was observed and then removed.
