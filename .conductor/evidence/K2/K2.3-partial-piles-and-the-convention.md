# K2.3 — the partial-file piles become responsibility folders, and one convention is written down

Session #7, stage K2. Follows `b05efef` (K2.1+K2.2) on `feat/karvan`.

## The measurement that decided the shape

The spec calls `ControlPlaneDto` "30 partial files". It is not partial at all. Listing every type
declaration per file:

```
ControlPlaneDto.Bugs.cs        -> BugDto, BugsDto, KnowledgeWriteResultDto
ControlPlaneDto.Lanes2.cs      -> (events pile, same tell)
ControlPlaneDto.Discovery.cs   -> ControlPlaneInfo
...29 files, 67 independent top-level records, none of them part of any type called ControlPlaneDto
```

The only `ControlPlaneDto` that existed was a **static mapper class** in `ControlPlaneDto.cs`, sharing
that file with `StateDto` and `ControlPlaneJsonContext`. So the `ControlPlaneDto.` prefix on 29 files
was a filing convention wearing a type's name — exactly what the spec suspected, and it means the fix
is a file reorganisation with no type surgery.

`ConductorEvent` is the same fiction: `ConductorEvent.cs` declares the base record, and the other ten
files declare independent event records. `ConductorEvent.Lanes2.cs` is the giveaway — a numbered
filename is a name that ran out. `TelegramService.Dto.cs` / `.Dto2.cs` / `.Dto3.cs` is a third instance
of it, holding the Telegram Bot API's wire records rather than parts of the service.

The piles that are **real** partials were checked the same way rather than assumed:

```
VerdictEngine    8 files -> types: VerdictEngine
SessionRunner    6 files -> types: SessionRunner
RunLoop          5 files -> types: RunLoop
SqliteRunStore   7 files -> types: SqliteRunStore, BugRow, CarriedBugRow
ControlPlaneServer 11 files -> types: ControlPlaneServer
```

One type, one field set, split by aspect. Splitting those means inventing handler objects and threading
state through them — a redesign, not a reshape, and the stage says do not rewrite. They stay.

## What changed

### The endpoint contracts

```
src/Conductor.Core/Http/
  ControlPlaneMapper.cs        was the static class named ControlPlaneDto - it is a mapper, so it says so
  ControlPlaneJsonContext.cs   the source-gen serializer registry, on its own
  ControlPlaneDiscovery.cs
  Contracts/
    State/      StateDto, StageDtos, ConsoleLineDto, TimelineDtos, GitDtos, ScoreDtos
    Sessions/   SessionDtos, DigestDtos
    Plan/       PlanDtos, PlanCheckpointDto, PlanEditDtos, PlanImportDtos, PlanResultDtos, PlanQaDto
    Tasks/      TaskDtos, TaskWriteDtos, TaskRefineDtos, TaskSplitDtos
    Knowledge/  BugDtos, LedgerDtos, WriteRequestDtos
    Telegram/   TelegramStatusDtos, TelegramTokenDtos
    Processes/  ProcessDtos, ProcessKillDtos
    Control/    ControlRequestDtos, InjectAcceptedDto, ControlPlaneInfo, PromptPreviewDto, PromptBlockDtos
    OwnerQueue/ OwnerQueueDtos
```

`ControlPlaneDto.cs` (196 lines, three responsibilities) became three files: the `StateDto` contract,
the mapper, and the serializer registry. `ControlPlaneDto.Responses.cs` held `InjectAcceptedDto`
**and** `ProcessDto`/`ProcessesDto` — a drawer labelled "responses" — and was split across `Control/`
and `Processes/`.

The namespace stays flat, `Conductor.Core.Http`, for every contract. Deliberate, and written down in
`ARCHITECTURE.md` with the reason: the wire contract is a published protocol that the Face, `conductor
face` and the fleet scan all speak as one vocabulary, and ten namespaces would put ten `using` lines in
every server file to describe one payload. Folders organise the files; the namespace describes the
protocol. It also means this whole reshape needed no `using` churn at all.

### The events

`ConductorEvent.<x>.cs` → `src/Conductor.Core/Events/Kinds/<subject>Events.cs` — `RunEvents`,
`SessionEvents`, `StageEvents`, `GateEvents`, `TaskEvents`, `LaneEvents`, `MutatingLaneEvents` (the
former `Lanes2`), `PlanEvents`, `OwnerControlEvents`, `BlockedUntilEvents`, `TaskDetailEditedEvent`.
`Events/` itself now holds only machinery: the base type, the log, the projection, the metrics.

### The Telegram API types

`TelegramService.Dto{,2,3}.cs` → `Integrations/TelegramApi/UpdateDtos.cs`, `ChatDtos.cs`,
`GetMeDtos.cs`. Seven records that belong to Telegram's API, not to our service.

## The convention

`ARCHITECTURE.md` (new, at the repo root — K2.4 adds the rest of the map to it). One rule, four cases:

1. **A file is named after what it declares.** A number appended to a filename is a name running out. If
   the prefix names a type the file does not declare, the prefix is a filing convention pretending to be
   a type — split it.
2. **A partial is legitimate when it is one type with one identity, split for size.** The test: open the
   file. If everything in it operates on the parent type's fields, the partial is real. If it declares
   independent types that merely *relate* to the parent, it is a pile.
3. **Endpoint contracts** go in `Http/Contracts/<feature>/`, one file per exchange (request + result
   together), under the single `Conductor.Core.Http` namespace — then registered in
   `ControlPlaneJsonContext` or they will not serialise.
4. **Events** go in `Events/Kinds/<subject>Events.cs`, never beside the code that raises them —
   `ArchitectureBoundaryTests.EventTypesStayInTheEventNamespace` fails the build if they do.

`ARCHITECTURE.md` closes with the table this checkpoint owes: every pile split, every pile left, and
the reason for each.
