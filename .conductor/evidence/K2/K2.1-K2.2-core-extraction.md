Session #7, stage K2, attempt 1. Commit `b05efef`.

## What was measured before anything moved

The extraction was scoped from measurement, not from the design doc's description of the problem.

| Question | Command | Answer |
|---|---|---|
| Where is Spectre under `Core/`? | grep `Spectre` over `src/Conductor/Core/**` | **3 files, comment/pragma text only** — `Core/Http/ControlPlaneDto.cs:19`, `Core/Planning/PlanDiscovery.cs:32`, `Core/Watch/SupervisorPolicy.cs:115`. No code dependency at all. |

| Do namespaces match folders? | first `namespace` line of all 335 files, grouped | **One-for-one** (`Core/Store` → `Conductor.Core.Store`, …). So the move needed **no namespace churn** — only the hosting half that deliberately left the `Conductor.Core.*` tree. |
| What actually points backwards? | grep `Conductor.Commands` / `ControlPlaneServer` from `Core/**` | **Exactly two**, both fixed below. |

That last row is the finding that made this a one-session checkpoint rather than a rewrite.

## The split

```
src/Conductor.Core/     domain, orchestration, store, events, providers, integrations,
                        planning, watch, fleet, update, face, models  (RootNamespace Conductor.Core)
src/Conductor/          Program.cs, Commands/**, Http/ (11 ControlPlaneServer partials),
                        Hosting/ConductorHost.cs                      — CLI + hosting

Conductor  ->  Conductor.Core  ->  Conductor.Planning     one way, enforced by the csproj graph
```

* `src/Conductor/Conductor.csproj:22` — the only `ProjectReference` is `..\Conductor.Core\Conductor.Core.csproj`.
* `src/Conductor.Core/Conductor.Core.csproj` — references **no** Spectre package and **no** ASP.NET; a reverse `ProjectReference` cannot be added without a circular-reference build error.
* Wire **contract** (`ControlPlaneDto*`, `ControlPlaneJsonContext`, `ControlPlaneInfo`) stays in core: `Core/Fleet/FleetScan.cs` reads *other* runs' discovery files and must speak it. The **server** is hosting and left.

### The two real backwards references, and what replaced them

1. `Core/Integrations/McpTaskServer.Handlers.cs:278,280` called `Conductor.Commands.BgStatusHandler.FormatDuration` — a core service reaching into the CLI for a string format. Now `Conductor.Core.HumanDuration.Format`, in core where a duration format belongs; `BgStatusHandler` calls the same one.
2. `Core/Fleet/FleetScan.cs:160,184` called `ControlPlaneServer.DiscoveryPath` — core reaching into hosting for a path convention. Now `Conductor.Core.Http.ControlPlaneDiscovery.PathFor`; the **convention** is core, the **server that writes the file** is hosting. `ControlPlaneServer.DiscoveryPath` is deleted, not forwarded.

`IReportsStartOutcome` moved the *other* way — into core — because `TelegramService` implements it.

## The regression the move caused, found and fixed rather than shipped

`BuildInfo.Current` reads **its own** assembly's attributes (`BuildInfo.cs:30`). `BuildInfo` moved to core, but `MinVer` + the `StampBuildInfo` target were on `Conductor.csproj` alone — so `conductor version`, `doctor` and `GET /version` all went blank **while the build stayed green**. Caught by `BuildInfoTests`, `ControlPlaneServerTests.GetVersion_*` and `SC8_2VersioningTests` in the first full run.

Fix: `src/BuildStamp.targets`, imported by **both** projects. `SC8_2VersioningTests.TheProjectFileCarriesNoHandTypedVersion` now resolves the `<Import>` and asserts the no-hand-typed-version rule for **both** assemblies instead of one — a stronger test than before, not a relaxed one.

## K2.2 — the rules, as tests that name the offender

`tests/Conductor.Tests/ArchitectureBoundaryTests.cs`, 8 facts, in the ordinary suite (so in `engine-full`):

| Test | Rule | How it knows |
|---|---|---|
| `CoreDoesNotLinkTheCliOrAnyUiAssembly` | core links neither `conductor` nor `Spectre*` | `Assembly.GetReferencedAssemblies()` — what the build linked |
| `CoreDoesNotHostHttp` | no ASP.NET reference, no `HttpListener` in core | assembly refs **and** a source scan (the BCL listener needs no package) |
| `CoreSourceNeverNamesTheShell` | no `Conductor.Commands` / `.Hosting` / `.Http` / `Spectre.Console` in core source | source text, comments stripped |
| `TheStoreDoesNotWriteToTheConsole` | store persists, does not present | source scan of `Conductor.Core/Store/**` |
| `CommandsDoNotReachIntoOrchestrationInternals` | no `SessionRunner`/`RunLoop`/`VerdictEngine`/`GateOrchestrator`/`RunContext` in `Commands/**` | source scan, comments stripped |
| `EventTypesStayInTheEventNamespace` | every `ConductorEvent` subtype lives in `Conductor.Core.Events` | reflection over both assemblies |
| `NoCoreDomainTypeRemainsInTheShellAssembly` | the split cannot quietly un-split | reflection over the shell assembly |
| `TheProjectReferenceDirectionPointsOneWayOnly` | the shape that makes the rest impossible | `Include=` attributes of both csprojs |

Comments are stripped before every source scan: `DoctorCommand.cs:210` and `ReportCommand.cs:69` legitimately *name* `SessionRunner` and `RunContext` in doc-comments explaining why they do **not** use them, and a rule that punishes the explanation teaches the next session to delete it.

`ArchitectureTests.CoreDoesNotDependOnTheCliOrAnyUi` scanned `src/Conductor/Core`, which the move deleted — left alone it would have gone green over an **empty set**. Repointed to `src/Conductor.Core`.

No architecture-DSL dependency was added. Every rule above is either "what did the compiler link" or "what does the source say" — the two questions ArchUnitNET would answer for us, at the price of a third-party package in the test project and a second, differently-shaped way to write a rule in a repo that already has `ArchitectureTests` in exactly this style. The rules are the deliverable; the syntax is not.

## Two things found on the way, filed not fixed

* A brand-new `run.db` logs `SQLite Error 19: FOREIGN KEY constraint failed` on the first `run_state` write at startup (scratch log above). Tolerated by `SqliteRunStore.TryExecute`, so the run continues — but it is a real first-write ordering defect on a fresh database, visible only because this proof created one.
* `InternalsVisibleTo("conductor")` on `Conductor.Core` is deliberate and documented in the csproj: the boundary K2.1 enforces is the **direction**. Promoting every member the shell already touches (`SyncCancellation`, `PromptBuilder.BuiltIns`, `SqliteRunStore.SetRunId`, `TelegramService`'s diagnostic fields read by `/telegram`) to `public` would be the rewrite this stage is told not to do. `ControlPlaneServer.Telegram` reading `TelegramService`'s private-ish fields is the one that deserves a seam — K2.3 territory.
