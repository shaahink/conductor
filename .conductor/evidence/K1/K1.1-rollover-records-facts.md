# K1.1 — a rolled-over session records the commits and claims it actually made

**Checkpoint:** K1.1 · **Branch:** `feat/karvan` · **Date:** 2026-08-04

## The defect, at the line

`src/Conductor/Core/Orchestration/SessionRunner.cs` — the rollover branch set
`rec.Outcome = SessionOutcome.RolledOver`, wrote the handoff and **returned before the verdict
pass**. The two fields the ledger reads are filled only there:

- `rec.NewCommits` ← `VerdictEngine.CollectCommits` (`VerdictEngine.cs:68`), whence the `commit_count`
  column written at `RunLoop.Plumbing.cs:192`.
- `rec.NewlyDone` ← the W1.3 claim rule, previously inline in `EvaluateSessionAsync`.

Nothing in `SessionRunner*.cs` touched either. So a rolled-over session's record was empty of both
whatever the agent had really done: `commit_count` 0 on 100% of rollovers across both Sarban runs,
against git ground truth of 91%.

## The change

| File | Line | What |
|---|---|---|
| `src/Conductor/Core/Orchestration/VerdictEngine.Claims.cs` | 71 | `ResolveClaims` — W1.3's claim rule (work graph, tracker-flip legacy fallback) lifted out of `EvaluateSessionAsync` so there is ONE rule, not two. |
| `src/Conductor/Core/Orchestration/VerdictEngine.Claims.cs` | 101 | `RecordRolloverFacts` — collects commits + satellite commits, notes outside-repo writes, resolves claims by that same rule, queues them for confirmation. Facts only. |
| `src/Conductor/Core/Orchestration/VerdictEngine.cs` | 322 | delivery path now calls `ResolveClaims` (behaviour identical, one rule). |
| `src/Conductor/Core/Orchestration/VerdictEngine.cs` | 372-376 | `PendingConfirmation` is a UNION, not a replace — a claim queued by a session that never reaches the verdict (rollover, audit, verify) is no longer dropped the moment the next delivery session claims anything. |
| `src/Conductor/Core/Orchestration/SessionRunner.cs` | 423 | the rollover branch calls it, before the handoff hint. |
| `src/Conductor/Core/Orchestrator.cs` | 94 | delegate wired. |

**What did NOT change** — the semantics of a rollover. `RecordRolloverFacts` does not touch
`AttemptsThisStage`, runs no gate battery, advances no workflow step. The branch still returns
before `_evaluateSession`.

## Proof — `tests/Conductor.Tests/K1_1RolloverRecordsFactsTests.cs`

A live harness test: a real scratch repo, a stand-in agent that commits **and claims through the
real `conductor task --done` CLI in its own process**, then reports 15 tokens against a plan cap of
10, so session #1 itself rolls over.

It asserts, in order: the CLI claim exited 0 · outcome is `RolledOver` · git ground truth over the
session's own window contains the agent's commit · `NewCommits` contains it · `NewlyDone` contains
`H0.1` · the `run.db` session row has `outcome=RolledOver` **and `commit_count > 0`** · the
checkpoint row is `DONE` with the agent's own evidence path and a **real sha** (not the `-`
placeholder an empty commit list forces) · `AttemptsThisStage == 0` · `GateSummary` empty and
`QueryGatesForSession` empty · outcome is not `Advanced` · the claim is in `PendingConfirmation`.

```
Passed!  - Failed: 0, Passed: 1, Skipped: 0, Total: 1, Duration: 4 s
```

### Falsification probe (the test pins the bug, it does not just agree with the code)

With `_recordRolloverFacts(...)` at `SessionRunner.cs:423` disabled and everything else identical:

```
Failed  K1_1RolloverRecordsFactsTests.ASessionThatRollsOver_RecordsItsCommitsAndItsClaims_...
  Error Message:  Assert.NotEmpty() Failure: Collection was empty
  at ...K1_1RolloverRecordsFactsTests.cs:line 150
```

Line 150 is `Assert.NotEmpty(rolled.NewCommits)` — and the git ground-truth assertion immediately
above it PASSED, i.e. the commit really existed on disk and the record really was empty. That is
the bug, reproduced and then closed.

## Trap paid for, recorded here so the next session does not pay it again

The first draft wired the stand-in agent through `cmd.exe /c script {prompt}`. A real composed
session prompt runs past cmd's 8191-character command-line ceiling; the child died with
`The command line is too long` before executing one line, and the engine recorded a plain
`AgentError` (exit 1) with no hint of the cause. Live harness agents must use the
`powershell -File` form (32767-char limit), as `P5RolloverLiveTests` does. This is the test-side
face of open bug #21.
