# K3.2 — `conductor history` browses past runs, and the Face can open one

Session #10, stage K3, attempt 1. Commits `ec1f158` (core), `f5de8a9` (CLI), `567b22a` (Face).

**Done when** (spec, `docs/history/CONDUCTOR-KARVAN.md` §K3.2): `conductor history [--repo|--plan|--since]`
lists past runs from the catalogue with their outcome, checkpoints, sessions and cost; a run can be
opened read-only and its spine replayed; the Face lists past runs in its run picker (extend
`runpicker.go`); and read-only means read-only — no verb in this checkpoint may mutate a finished run.

---

## 1. Read-only is enforced by the connection, not by discipline

`src/Conductor.Core/History/RunArchive.cs:33-40` opens `Data Source=<db>;Mode=ReadOnly;Cache=Private`.
The type has **no write method on it**, and each read opens and closes its own connection, so browsing
never becomes a reader a live engine's writer waits behind.

It is deliberately not `SqliteRunStore`. That constructor
(`src/Conductor.Core/Store/SqliteRunStore.cs:18-39`) does three writes before the first read:
`Directory.CreateDirectory`, `PRAGMA journal_mode=WAL`, and `EnsureSchema` → `MigrationRunner.Run`.
Pointing it at a run from July rewrites that run's schema just to look at it.

Measured, not asserted — `tests/Conductor.Tests/K3_2HistoryTests.cs`:

| test | what it measures |
|---|---|
| `Archive_cannot_write_because_sqlite_itself_refuses` | an `INSERT` and an `UPDATE` through the archive both raise `SqliteException` containing `readonly`; the run's status is unchanged afterwards |
| `Browsing_an_older_schema_does_not_migrate_it` | a database pinned at `schema_version = 2` is listed successfully and is **still** at version 2; `LastWriteTimeUtc` is identical; no `-wal` file is created |
| `Listing_does_not_restamp_the_catalogue_it_is_reading` | `List` + `Find` leave `catalogue.json`'s `lastSeenUtc` alone — browsing must not reorder the list it is showing |

23 tests in `K3_2HistoryTests`, all green. 6 more in `face-go/internal/tui/runpicker_test.go`.

## 3. The Face's picker lists what the machine remembers

`runpicker.go` **extended**, not duplicated: `WithPast` is chained rather than a second `NewPicker`
parameter, so every existing caller and test is untouched —
`TestPickerWithoutHistoryIsUnchanged` renders the picker with and without an empty history and
compares the frames byte for byte.

Read-only is in the interaction, not only the wording:

- `TestEnterOnAPastRunAttachesToNothing` — the cursor reaches a past row, the detail line reads
  `read-only (no engine to attach to)`, `enter` returns **no** `tea.Quit` command, `Chosen()` still
  reports nothing chosen, and the hint becomes `conductor history e9e21d10`.
- `TestNumberKeysNeverReachAPastRun` — `2`, `3`, `9` attach to nothing when only one run is live;
  `1` still attaches.
- `The_face_envelope_carries_past_runs_and_never_the_one_that_is_live` (C#) — a run answering on a
  port is excluded from `past`, and the envelope carries the two lists separately.

Both new goldens were created with `-update` scoped to the new test alone; `git status` confirmed
the only golden changes were the two new files.

## 4. Two defects the rig found that the tests had not

**`--since` swallowed every absolute date.** `"2026-07-01"` starts with digits, took the
relative-window branch, found no unit suffix, and returned null — so the filter silently listed
everything. The relative form now only wins when the suffix is a real unit
(`RunHistory.ParseSince`), with six theory cases pinning it. Found by a test written after the
behaviour, and it failed on the first run.

**A `--plan` that matched nothing said "no runs in the catalogue"** — a different and much more
alarming claim than "your filter matched nothing".

## 5. A latent defect this rig measured — filed as bug #28

`C:\code\conductor\.conductor\run.db` has `schema_version = 9` while `sessions` already carries the
v10 `soft_break` column (`PRAGMA table_info` confirms both). Any engine at v10 or later dies opening
it:

```
error: SqliteException: SQLite Error 1: 'duplicate column name: soft_break'
   at Conductor.Core.Store.MigrationRunner.Apply(...)
```

Reproduced twice with the fresh build's `status` against the imported copy. Not a torn snapshot —
re-copying `run.db` + `-wal` + `-shm` reproduced it identically, so the `ALTER TABLE` landed without
the version row advancing. The published engine on PATH is pre-v10, so nothing has hit it yet; the
owner's K7.2 reinstall will.

It is also the sharpest argument for this checkpoint's design: **`conductor history` read that same
database and listed all three runs**, because it opens `Mode=ReadOnly` and never migrates.

## 6. What K3.2 deliberately does not do

`engine 0.0.0.0` / `2.0.0.0` in the header above is the assembly version, which answers nothing.
Which build produced a run, its commit, its dirty flag and the limits that governed it is **K3.3**,
and `history` already has the row to print it in.

The picker's history is only reachable when the engine hands over a fleet — two or more live runs,
or `--pick`. With zero live runs `conductor face` still says there is nothing to attach to. Making
that path offer history is a Face-side decision about attach semantics, not a read-only browse, and
it is not in this checkpoint's acceptance.
