## 1. The claim in the spec was wrong, and it was measured before anything was edited

K6.4's stage notes and the K6.3 handoff both said: *"Report, Knowledge and the handover panes render
markdown as plain text."* All three parts are false.

| claim | what the code does | file:line |
|---|---|---|
| Report renders markdown as plain text | Report is a stage/session/gate **dashboard**. Its only free text is `*s.AttentionReason`, one line. | `tab_report.go:142` |
| Knowledge renders markdown as plain text | Bug detail and ledger content are **flattened** — `strings.ReplaceAll(…, "\n", " ")` then `truncate` — to one row each. | `tab_knowledge.go:205`, `:229-233` |
| there are handover panes | **There is no handover pane in face-go.** The only occurrence of the word is a fake command string in a demo fixture. | `internal/api/demo.go:365` |

Report's and Knowledge's rows are exactly the dense single-line lists adr/0006 §5 keeps plain **on
purpose**. Rendering markdown into them would be a regression, not the checkpoint.

The two surfaces that were genuinely wrong:

- **the session result summary** (`tab_history.go:407`) — rendered markdown, in a hard-coded palette;
- **the compiled-prompt preview** (`tab_templates.go`) — the longest document this Face shows, painted
  flat and, more importantly, **not scrollable at all**.

## 2. The renderer takes the theme, and glamour stops running per frame

`renderMarkdown` set `glamour.WithStandardStyle("dark")` unconditionally (`markdown.go:22`, before).
On `latte` — a light scheme — an agent's result summary was near-white prose on a near-white pane, and
the theme system stopped at the edge of every markdown block.

`markdownStyle(theme)` now projects the palette's **roles** onto glamour's style config: no hex is
named, only `theme.Text`, `theme.Accent`, `theme.Base`, `theme.Overlay`, `theme.Surface`,
`theme.Peach`, `theme.Blue`, `theme.Teal`, `theme.Green`. It starts from glamour's dark **or light**
base config, chosen by `Theme.IsLight()` — WCAG relative luminance of `Base`, the same formula the
contrast gate uses (`internal/widgets/color.go`).

Measured, from the driven frames (`K6.4-frames.txt`, sections 4–5):

| | mocha | latte |
|---|---|---|
| `Theme.IsLight()` | `false` | `true` |
| body prose | `#CDD6F4` | `#4C4F69` |
| H1 fill | Base on Accent `#CBA6F7` | Base on Accent `#8839EF` |
| inline `` `RunDb` `` | Peach on Surface | Peach on Surface (light values) |
| link / link text | Blue / Teal | Blue / Teal |

`TestMarkdownTakesItsColoursFromTheActiveTheme` asserts on the emitted 24-bit SGR triples built **from
the theme roles**, not from hard-coded hexes, so the test cannot drift from the palette. It also
asserts the negative — the latte render must not carry mocha's text colour — because "the two outputs
differ" would pass on a wrapped line alone.

### The per-frame render, measured

The old renderer was called from inside `View`, re-running goldmark plus chroma on every tick,
keystroke and resize. Output is now memoised on `(theme, width, source)`.

```
200 renderMarkdown calls of unchanged content invoked glamour 1 time(s)
```

`TestMarkdownRendersOncePerFrameStorm` pins that, and pins the other half — a width change, a content
change and a theme switch each invoke glamour exactly **once more**, so the memo is a cache and not a
freeze. `rebuildStyles()` drops it on every theme apply (`view.go`).

## 3. The compiled-prompt preview: a viewport, and deliberately NOT markdown

This pane was `truncateLines(prompt, paneRows-5)` with **no scroll of any kind** — the last
read-not-select body that was not a viewport (adr/0006 §5). A session prompt is the longest single
document this Face shows and it was readable down to its first ~25 lines and no further.

It now scrolls through a `viewport.Model` behind the one scroll idiom. Driven proof
(`K6.4-frames.txt`, sections 1–3): a 90-line prompt, `end` pressed once.

```
preview scroll state: 94 lines in 19 rows, offset 75, atBottom=true, status "100%"
LAST-LINE: conductor task --done <id> --evidence <path>
←→ kind · ↑↓ d/u G/home scroll 100% · v/esc close
```

**Markdown was considered for this pane and rejected on evidence.** glamour sanitises anything that
parses as an HTML tag, so the placeholders a prompt is full of are silently deleted:

```
source   : conductor task --done <id> --evidence <path>
markdown : conductor task --done  --evidence
the pane : conductor task --done <id> --evidence <path>
```

A pane whose whole job is to show an owner the exact bytes an agent will be handed cannot afford that.
`TestTemplatesPreviewKeepsPlaceholdersMarkdownWouldEat` guards both halves, and **skips with an
instruction** if glamour ever stops stripping them — so the reason this pane stays plain cannot quietly
become untrue.

Tests: `TestTemplatesPreviewReachesTheEndOfALongPrompt`, `…BindsTheOneScrollSet`,
`…OffsetIsClampedInUpdate`, `…StartsANewKindAtTheTop`.

## 4. Bug #30's last live instance, on the owner's own list

adr/0006 §5 names the owner-queue full view as a viewport surface; K6.2 did not reach it. What was
left there was not a style gap — it was **bug #30 itself, unfixed**:

```go
case "down", "j":
    m.home.queueScroll++ // clamped by the renderer against the real body height
...
scroll := min(m.home.queueScroll, maxScroll)   // in View, on a value receiver
```

Unbounded increment in Update, throwaway clamp in the renderer: identical to the Report defect the
owner reported. `queueScroll` is now a `viewport.Model`.
`TestOwnerQueuePastTheEndCostsExactlyOneKeyToComeBack` is the same measurement panescroll_test.go
already makes for Report and Knowledge. The pane also gains `d`/`u`/`end`/`G` — it bound five keys by
hand and had **no way to reach the end of a queue at all**.

Driven proof (`K6.4-frames.txt`, section 6): 40 items, `end` pressed once —
`201 lines in 24 rows, offset 177, atBottom=true, status "100%"`.

`owner_queue_pane.golden` and `home_owner_queue.golden` are **byte-identical**: the frame did not move,
only the machinery under it.

## 5. The primitive swaps: what is done and what is named

| ADR §5 item | status |
|---|---|
| `viewport` on every read-not-select body | Report + Knowledge (K6.2); **compiled-prompt preview and owner-queue full view (K6.4)**. Remaining: Agent raw (`consoleScroll`) and Kanban detail — see below. |
| `bubbles/list` | **Decided NO** in K6.1. Not a K6.4 gap. |
| `bubbles/table` | **Decided NO** in K6.1. Not a K6.4 gap. |
| `bubbles/textarea` replaces `widgets/editor.go` | **Left, with a measurement — bug #31.** |
| `bubbles/spinner` / `progress` | Left. The ADR admits them "only where they do not disturb a golden"; both would move goldens for no reader benefit. |

**Why the textarea swap is not in this checkpoint (bug #31).** `textarea.Update` takes a `tea.Msg`,
but this Face routes keys as `msg.String()` from `update.go:36` down through `handleKey(key string)`:
**72 non-test and 148 test call sites, 220 in all**. Threading `tea.KeyPressMsg` through that is a
K6.3-sized refactor, not a primitive swap, and synthesising a fake `KeyPressMsg` from a string is a
lossy adapter. The defect it would fix is real and measured — `widgets.TextArea` **clips** every line
except the caret's (`editor.go` `renderLine` → `clipLine` for `row != cy`) — and is now tracked rather
than forgotten.

**Two viewports still outstanding, named rather than silently skipped:** Agent raw
(`tab_agent.go:27`, `consoleScroll`) is a *tail-anchored* model — it clamps in Update at
`tab_agent.go:140-141`, so it does **not** carry bug #30's shape and the conversion is a redesign of
its live-tail semantics, not a lift. Kanban detail (`tab_kanban_detail.go`) has no scroll state at all
and caps each block at four lines; giving it a viewport means deciding what the pane's document *is*,
which is a design question, not a swap.
