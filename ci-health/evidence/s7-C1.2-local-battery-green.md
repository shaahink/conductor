## The second failure the battery found, and why CI could never see it

The first battery run (`.conductor/bg-logs/powershell-20260803-150516441.log`) was still red after
the C1.1 fix, but on a *different* test:

```
Conductor.Tests.SC3_4AdvisorTests.NoShippedPlanCarriesAnAdvisorKeyNothingReads [FAIL]
  Assert.NotNull() Failure: Value is null
  at ...SC3_4AdvisorTests.RepoRoot() in SC3_4AdvisorTests.cs:line 256
Failed!  - Failed: 1, Passed: 1772, Skipped: 0, Total: 1773
```

Root cause: that class's `RepoRoot()` walked up the tree looking for a `.git` **directory**.
`C:/Code/conductor-ci` is a linked git **worktree**, where `.git` is a 54-byte *file* holding a
`gitdir:` pointer:

```
$ ls -la .git
-rw-r--r-- 1 shahi 197609 54 Aug  3 14:27 .git
```

So the walk ran off the top of the filesystem, `dir` became null, and the test died on
`Assert.NotNull` — meaning its actual assertion (`Assert.Empty(offenders)` over
`plans/*.plan.json`) had **never run in a worktree at all**. GitHub Actions does an ordinary clone,
where `.git` is a directory, so CI cannot reproduce this.

The fix accepts `.git` as either a file or a directory. This **strengthens** the test: the plan
check now actually executes in a worktree instead of dying before it. Nothing was relaxed, skipped
or removed — the suite total is 1773 both before and after. It is the only `RepoRoot()` in the repo
that used the directory test; every other one keys off `Conductor.slnx`, which is why no other class
was affected.

This matters beyond this session: `C:/Code/conductor-ci`, `C:/Code/conductor-cihealth` and
`C:/Code/conductor` are all worktrees of the same repository, so any session running the battery in
any of them would have hit it.
