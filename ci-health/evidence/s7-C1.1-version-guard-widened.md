## The measurement that shows the two algorithms legitimately disagree here

```
$ git describe --tags --long --match v[0-9]*
v0.3.0-10-g2151cf0                     <- describe height = 10

$ git log --merges --format=%H v0.3.0..HEAD | wc -l
2                                      <- two merges of feat/sarban sit inside the range

```

guard never fired: it asked `git log -1 --format=%P HEAD` and saw one parent.

## What actually changed

The guard was widened from *"is HEAD a merge commit"* to *"does the range from the newest tag to
HEAD contain any merge"* — one `git log --merges v<base>..HEAD` call, where `<base>` is the tag
`git describe` already reported. The old question was about the tip; the divergence is a property of
the range, so every ordinary commit stacked on top of a merge inherited the gap and ran a strict
equality it could not satisfy. That is why master was green at 19:07 on 2026-08-01 and red at 19:25
on a docs-only commit.

A failed `git log` query is treated as "cannot tell", which takes the same branch as "there is a
merge": the strict height equality is the optional half of this test, and a git problem should not
be reported as a versioning defect. The shape assertion runs regardless of that outcome.

## What was NOT done

- The test was not deleted, skipped, or marked `Skip=`.
- The `-alpha.0.N` regex assertion was not relaxed — it is untouched and still runs on every path.
- No number was hardcoded to make the equality pass.
