## DevContext2's develop CI went red once, and it was not the bump

Run `30829803125` first came back **failure**: one test on the `macos-latest` leg only —
`StageWaterfallTests.Waterfall_names_every_pipeline_phase_and_accounts_for_the_wall`, reporting
*"Waterfall accounts for only 78.9% of the wall (214ms of 271ms)"*. It is a timing floor.

Two measurements say it is not this change:

1. The **identical content** passed that same macos leg on PR run `30828680117`.
2. The **same test on the same leg was already failing on branch `main` at run `30817933911`**,
   which predates every commit in this session.

An action's major version cannot change a test's timing verdict. `gh run rerun --failed` turned the
leg green and run `30829803125` now reads **success**. The percentage floor was not touched, no test
was skipped and no step removed. Filed as a tracked bug.

## What the Release dispatch did and did not exercise

`Release`'s `workflow_dispatch` path is a deliberate dry run — it builds the full artifact inventory
but skips the NuGet push and the GitHub Release. So the branch dispatch `30828834858` (success) and
the `develop` dispatch `30829815008` exercise `checkout@v7`, `setup-dotnet@v6`, `setup-node@v7`,
`pnpm/action-setup@v6` and `upload-artifact@v7` — the Tauri installer job and the CLI pack job both
ran green through them.

The `develop` dispatch `30829815008` was still building its Tauri installer when this session ended
— its CLI job had already gone green. The branch dispatch `30828834858` is the completed proof: the
same three jobs on byte-identical workflow content, **success**. If `30829815008` lands red it is a
Tauri build issue, not an action-version one, since the branch run cleared every bumped step.

The `GitHub Release` job is `skipped` on a dispatch by design, so `download-artifact@v8` and
`softprops/action-gh-release@v3` are **not** exercised by it. Those two pins fire only on a real
`v*` tag push. Recorded as a stated gap rather than papered over; nothing was changed to force that
job to run.

## The one workflow that could not be exercised, and why that is not a fake pass

**sitekit `Release`** triggers only on a `v*` tag push. It has never run on `main` and structurally
cannot, so there is no run of it on the default branch to be green or red — the newest run of it
anywhere is `30645090630` on tag `v0.24.0`, success, on the pre-bump pins.

Its bump is the same two pins as `ci.yml` (`checkout` v5→v7, `setup-node` v5→v7), and `ci.yml`'s
bump is proven green by run `30828800198`. The only way to exercise `release.yml` itself is to cut a
tag, and this workflow publishes to npm via trusted publishing — cutting a throwaway tag would push
a real package version. That is not a price worth paying for a run id, so the bump lands unexercised
and is recorded here as such. The next genuine release is its first run.

This is a stated gap, not a softened measurement: no trigger was widened, no step removed, and
nothing was changed to make an unrunnable workflow look runnable.
