# B1.2 — lychee is given a root directory; no correct link was rewritten

## The failure, measured

Run `30812917017` (`Check links`, schedule, `main`) — 17 errors. Fourteen of them
read:

```
Cannot resolve root-relative link '/blog/designing-a-deterministic-kernel':
To resolve root-relative links in local files, provide a root dir
```

across eight post files, for links of the form `/blog/...`, `/projects#...` and
`/images/...`. These are **not** broken content. `rehypeBaseLinks` in
`astro.config.mjs` prefixes them with the `/site` base at build time; they are
correct as authored.

The workflow already declared its scope — `--scheme https --scheme http`, with the
comment "Only http(s) links: internal links are base-prefixed at build time and
would false-positive as file paths here." The bug was that lychee could not
*classify* a root-relative link without a root, so it errored per link before that
filter ever ran.

## The fix

`.github/workflows/links.yml`, commit `e033f74`: the lychee args gain
`--root-dir` set to the workflow's checkout directory, plus a comment explaining
why the scheme filter depends on it. Given a root, lychee resolves those links to
file URIs, and the existing scheme filter drops them as intended.

One further exclusion was added, anchored: the bare origin
`https://shaahink.github.io` with an optional trailing slash and nothing else.
That is `site.url` in `src/data/site.ts` — the deployment origin constant, not a
page (see B1.1 for why rewriting it would break the RSS feed). Because the pattern
is anchored at both ends, every real `https://shaahink.github.io/site/...` URL
remains under measurement.
