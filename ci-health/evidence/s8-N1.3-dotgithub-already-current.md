Session 8. `shaahink/.github`, cloned at `C:/Code/dotgithub`.

already on the current major:

| --- | --- | --- | --- |

| `content-request.yml` | `actions/setup-node` | v7 | v7 (v7.0.0) |

There are no composite actions and no other YAML in the repository — `.github/` contains only
`workflows/` and `ISSUE_TEMPLATE/`, and the repo root only `LICENSE` and `README.md`.

**So nothing was bumped, because nothing needed bumping.** This is the same shape session 7 found
in conductor: the bump half of the checkpoint was a measurement, not an edit.

## The careful file, and why its guard did not need re-proving

`content-request.yml` runs an agent, and the plan requires that if its credential guard cannot be
demonstrated to still hold after a bump, the file is left alone with the reason recorded.

That question does not arise here. The file is untouched — no bump was applied to it, so the
structural property it rests on (`persist-credentials: false` on the agent's checkout, and the
`guard-proof` job that commits in the agent's exact credential state and requires the push to be
refused) is bit-for-bit the property that was already in force. Re-running the proof would be
testing an unchanged file against an unchanged runtime.

Worth recording for a future session that *does* need to bump it: the guard proof is not
dispatchable from this repo. `content-request.yml` is `workflow_call`-only, and the proof runs
behind a `prove-guards` boolean input, so demonstrating it needs a **caller** repo invoking it with
that input set. No caller exists in the public fleet — `site-template` carries a `content-request`
*issue template*, not a workflow that calls this pipeline.

## The shared pipeline, proven downstream

`shaahink/.github` has **zero runs of its own** — both files are `workflow_call`-only, so the
repository's own Actions history is empty by design and can never be the evidence.

The evidence is a downstream caller. `site-template/.github/workflows/ci.yml` calls
`shaahink/.github/.github/workflows/site-ci.yml@main`, and after merging
[site-template #32](https://github.com/shaahink/site-template/pull/32):

| run | ref | event | conclusion |
| --- | --- | --- | --- |
| `30828982820` | `chore/node20-action-bump` | pull_request | success |
| `30829068429` | `main` | push | success |
| `30829094483` | `main` | workflow_dispatch | success |

All three ran `site-ci.yml@main` — the shared pipeline at its current pins — green.

The third of those exists because of the one change this checkpoint did land. `site-template`'s CI
had only `push` and `pull_request` triggers, which meant the pipeline it depends on lives in
another repository and there was no way to re-ask whether that pipeline is still green without
inventing a commit. PR #32 added `workflow_dispatch`, and run `30829094483` is that trigger firing
on `main` and coming back green. The fleet's shared site pipeline is now re-provable on demand from
a caller's default branch, which is what N1.3 needs it to be.
