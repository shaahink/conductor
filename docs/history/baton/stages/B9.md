# B9 — Task graph + smart session management

**Stage goal:** a lightweight, event-sourced task graph BENEATH the checkpoint contract, updatable by
the agent via MCP (persisting its todo list across sessions), plus cooperative session-breaking so a
long session ends cleanly and the next resumes at the next sub-task.

**Sessions:** ~3. **Persona:** planner. **Depends on:** B2 (events), B7 (planner persona),
B8 (rollover). **Branch:** `feat/baton-b9`.

## Why (findings)
- Checkpoints are coarse; a single `L3.2` can be a session-plus. opencode keeps an in-session todo
  list that dies with the session (F-8-adjacent). A persisted task graph makes "continue at the next
  sub-bullet" real.

## Requirements
- R9.1 Task-graph model (`TaskItem`: id, checkpointId, title, status, source) as an **event-sourced
  projection** (`TaskAdded`/`TaskStatusChanged`) — the checkpoint table stays the verified contract
  (D-8); tasks are advisory break-points (anti-pattern A16: keep lightweight).
- R9.2 Planner persona decomposes the active checkpoint into ordered sub-tasks at session start.
- R9.3 MCP task server exposing `task_list` / `task_update` / `task_add`, registered with the agent so
  it updates the shared graph live — persisting its todo list across sessions.
- R9.4 Cooperative soft-break: as budget/time nears the threshold, inject "finish the current
  sub-task, write handoff, end cleanly" → session ends → next session starts fresh at the next
  sub-task. Hard token-ceiling fresh-start (B8 `RolledOver`) as the fallback if ignored.
- R9.5 Task views in CLI (`conductor tasks`), TUI (a tasks pane), and Telegram (`/tasks`).

## Tasks → checkpoints
- **B9.1** — task-graph model + event-sourced store + `TaskGraph` projection.
  - Gate: tasks fold from events; a task's status change is replayable (test).
- **B9.2** — planner decomposition (planner persona seeds `TaskAdded` from the checkpoint + doc).
  - Gate: given a checkpoint, the planner produces ≥1 ordered sub-task recorded in the graph (test
    with fake/deterministic planner output).
- **B9.3** — MCP task server (`task_list/update/add`); agent config registers it.
  - Gate: a scripted MCP client calls `task_update` and the change appears in the projection (test).
- **B9.4** — cooperative soft-break + hard fallback.
  - Gate: fake-agent test — approaching the soft threshold injects the finish-and-handoff nudge and
    the next session starts fresh at the next sub-task; blowing the hard ceiling yields `RolledOver`.
- **B9.5** — task views.
  - Gate: `conductor tasks` lists the graph; TUI pane renders it (renderer test).

## Definition of done
A persisted task graph beneath the checkpoints, live-updatable via MCP, with cooperative
session-breaking that continues at the next sub-task. Full battery green.

## Traps
- Do NOT let the task graph become the source of truth (D-8) — the checkpoint table + gates remain
  the contract. Tasks guide; they do not gate.
- Soft-break needs agent cooperation (you can't clean-stop an LLM by killing it) — the nudge is a
  prompt injection; the hard ceiling is the safety net. Test both paths.
- MCP server must be read-mostly and safe: `task_add` shouldn't let the agent invent checkpoints,
  only sub-tasks under the active checkpoint.
